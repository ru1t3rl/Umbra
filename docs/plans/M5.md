## Goal
The engine becomes controllable from another thread and over the network without changing what it
simulates. An `EngineHandle` owns one engine thread (at least 4 MiB of stack). That thread loads
scenarios, applies commands between ticks, ticks by its clock, and publishes immutable per-tick frames
to bounded subscriptions that drop the oldest frame when full.

The optional `umbra-server` crate puts two things on top of that handle and nothing else:
- a REST API under `/api/v1`, with OpenAPI generated by `utoipa`, committed and drift-checked;
- a WebSocket stream (JSON), with its schema committed.

`umbra serve` starts the server. Deployment settings come from flags, an `umbra.toml` file, or built-in
defaults. Scenarios that omit `tick_rate_hz` run at a configurable default of 60 Hz, reported wherever
the run is reported. Per-tick state hashes are identical with and without the server.

M5 is the contract that M5b's GUI consumes: the generated TypeScript client, the stream schema, and
stepped mode for Playwright. The contract is therefore designed for M5b now and changes only additively
afterwards.

**Acceptance (spec section 17, M5):**
1. OpenAPI drift check passes (gate 10; AT-12, AT-11).
2. A script or generated client runs a scenario end to end (AT-14).
3. Slow-client test passes (AT-10, with AT-3).
4. Catalog and validate endpoints covered by contract tests (AT-8, AT-11).

**Gate check (step 1):** M4 is ticked in `docs/milestones.md` with evidence: tag `m4-done`, the full local

### Tick-rate default: frozen-test check (re-verified 2026-10-19 by the architect)
- **No test requires a missing `tick_rate_hz` to be an error.** No test in `crates/*/tests/**` or in an
  inline test module asserts `missing_key` for `tick_rate_hz`. The pinned rows are `tick_rate_hz = 0` and
  `-1` (`invalid_value`), `2.5` and `"30"` (`wrong_type`), and the error-collection row at
  `scenario_file.rs:826`. All of them keep their present value, so they pass unchanged.
- **Fixtures.** Of the fixtures, only `fixtures/scenarios/invalid_structure/missing_scenario_table.toml`
  lacks the key. It also lacks the whole `[scenario]` table, so the schema test

- **Every scenario fixture and example names `tick_rate_hz` explicitly**, with `30` or another fixed value.
  So every golden hash, every `duration_ticks` value and all stdout stay unchanged.
- **m2-compat check 2b (inline `#[cfg(test)]` regions).** `crates/umbra-templates/src/scenario_read.rs`
  has one inline test module (lines 735-784):
  - `duration_that_is_a_float_artifact_...` calls `Reader::new(&file)` and `read_settings(&mut reader, t)`

### Default tick rate (human decision 2026-10-19; ADR 0010 note, ADR 0029)
```rust
// umbra-core (additive)
pub const DEFAULT_TICK_RATE_HZ: u32 = 60;
// umbra-templates (additive)
#[non_exhaustive] pub struct LoaderOptions { pub max_subgraph_depth: u32, pub default_tick_rate: TickRate /* 60 */ }
#[derive(Debug, Clone, Copy, PartialEq, Eq)] #[non_exhaustive]
pub enum TickRateSource { Scenario, Default }
// Scenario gains: pub tick_rate_source: TickRateSource   (tick_rate keeps holding the effective rate)
```
**Reader rule.** An absent `[scenario] tick_rate_hz` yields `LoaderOptions::default_tick_rate` with
`TickRateSource::Default`, and `duration_ticks` uses that rate. A present value is read exactly as today,
with `TickRateSource::Scenario`; all existing diagnostics stay. `read_settings` and `Reader::new` keep
their signatures (check 2b): a `Reader` field carries the default, `Reader::new` sets it to 60, and the
loader overwrites it from its options.

**Precedence.**
1. An explicit scenario value always wins; it is a determinism input.
2. Otherwise `[simulation] tick_rate_hz` from `umbra.toml`.
3. Otherwise 60.

No CLI flag and no REST field override a scenario's rate (decision 9, the simplest option): the scenario
file is the place to set it.

**Visibility (reproducibility).**
- `SessionInfo` and `ScenarioInfo` carry `tick_rate_hz` and `tick_rate_source`, and so do `GET
  /api/v1/status` and the frame `run` status.
- `umbra run` and `umbra validate` write `note: <file>: tick_rate_hz not set; using <hz> Hz (<built-in
  default | default from <config path>>)` to **stderr** whenever the default applied. Stdout is unchanged,
  so goldens and the four-process byte-identity tests hold.
- Determinism docs: for a scenario that omits the key, the effective rate is part of the run's inputs;
  M7 recordings store it.

**Engine plumbing.**
```rust
#[non_exhaustive] pub struct LoadSettings { pub default_tick_rate: TickRate, pub extra_plugin_paths: Vec<PathBuf> }
impl Default for LoadSettings { /* 60 Hz, no paths */ }
pub fn load_scenario_with_settings(base: &Registry, path: &Path, settings: &LoadSettings) -> Result<LoadedScenario, ScenarioError>;
pub fn validate_path_with_settings(base: &Registry, path: &Path, settings: &LoadSettings) -> Result<ValidationReport, ScenarioError>;
```
The existing `load_scenario*` and `validate_path*` functions use `LoadSettings::default()`. Because
every existing file names its rate, their results are unchanged.

### Configuration file `umbra.toml` (ADR 0029)
- **Read by** `umbra-templates::config` with the existing located TOML reader: `read_config(&SourceFile)
  -> Result<ConfigFile, Diagnostics>`. It is re-exported by `umbra-engine` and mapped by `umbra-cli` into
  `LoadSettings`, `HandleConfig` and `umbra_server::ServerConfig`.
- **Contents.** `ConfigFile` holds plain optional values per section: `simulation.tick_rate_hz`,
  `plugins.paths` (resolved against the file's directory), `log.level`, `server.{bind: SocketAddr,
  scenario_root, body_limit_bytes, command_queue}`, and `server.stream.{default_rate_hz, max_rate_hz,
  queue_frames, max_events_per_frame, send_timeout_s}`.
- **Validation.**
  - `schema_version` is optional; a newer value is `unsupported_schema_version`.
  - Unknown keys are `unknown_key`, at any level.
  - Value errors are `wrong_type` or `invalid_value`, located, and all of them are reported.
- **Schema.** `schemas/config.v1.schema.json` (`$id` `urn:umbra:schema:config:v1`), printed by `umbra
  schema config`.
- **Location.**
  1. `--config FILE`. A missing named file is exit 1.
  2. Otherwise `./umbra.toml` if it exists.
  3. Otherwise built-in defaults.

  The file used is logged at info level.
- **Precedence:** CLI flag > config file > built-in default, per setting. Lists replace, they do not
  merge: `--plugin-path` replaces `[plugins] paths`, and a scenario's own `plugin_paths` follow either.
- **`bind` is one key**, not `host` + `port`. It mirrors `--bind` one to one (a flag replaces the whole
  address), parses as `SocketAddr`, and handles IPv6 (`"[::1]:7878"`) without special cases.
- **Defaults:** `127.0.0.1:7878`, scenario root = the working directory at startup, 1 MiB body, queue
  64, stream rate 30 (max 60), 4 frames, 4096 events, 10 s send timeout, `warn`, 60 Hz. A non-loopback
  bind from any source logs the no-authentication warning.
- **Consumers.** `run`, `validate`, `list-plugins` and `serve` all read the file, so that `validate` and
  `run` agree on `duration_ticks`. Each command uses the keys that apply to it.

**Engine thread loop.** This one thread is the only one that touches an `Engine`:
```
loop:
  apply every queued command (try_recv) in arrival order; state changes publish a Control frame
  if no session, or the clock is idle (paused, ready, stopped, stepped without steps): block on recv()
  else match session.engine_mut().pump(max_wait):
      Ticked(report) -> collect report.events; complete step replies whose target tick was reached;
                        if tick >= duration_ticks: stop(Duration), cancel pending steps (reply reached);
                        publish a Tick frame (if anyone subscribes)
      Waited | Idle  -> continue
      Err(PluginFault) -> stop(PluginFault), publish the faulting tick's frame, cancel steps
      Err(other)       -> stop(Error), cancel steps
  on channel disconnect or shutdown: drop the session (plugins shut down here), exit
```
- **Load.** A load creates the `Session` with `config.load` (its default tick rate applies only to
  scenarios that omit the key) and pauses its engine at tick 0 (`ready`). `start` resumes it.
- **Step.** `step(n)` requires `running` and the stepped clock. It calls `request_steps(n)` and replies
  when `tick >= start + n`. It replies with `StepCancelled { reached }` instead on pause, stop, unload, a
  clock change away from stepped, or a fault.
- **Applied tick.** Every state-changing reply carries the tick it applied at (`applied_at`); this is
  recorded for M7 replay.

### `umbra-api-types` (D-12; ADR 0026, 0027)
**Conventions.**
- All DTOs derive `Serialize, Deserialize, ToSchema`; enums use `#[serde(rename_all = "snake_case")]`.
- `#[serde(deny_unknown_fields)]` is on **requests** only; responses stay open for additive fields.
- IDs are strings. The server checks their grammar with the core constructors (`422 invalid_id`).
- Units go in the field-name suffix (`_deg`, `_m`, `_mps`, `_s`, `_hz`), as in the file formats (REQ-C-4).
- Constants: `pub const API_VERSION: &str = "1.0.0"; pub const STREAM_PROTOCOL: &str = "umbra.stream.v1";`
- `state_hash` is the 16-digit lower-case hex form the CLI prints.
- Entity ids and ticks are JSON integers, exact in JavaScript below 2^53 (documented).

**DTO groups.**
- `status`:
  - `EngineStatus` and `ScenarioInfo`, both with `tick_rate_hz` and `tick_rate_source: scenario | default`;
  - `RunState`, `StopReason`;
  - `ClockSetting`, tagged: `{ "mode": "afap" | "realtime" | "stepped" | "scaled", "scale"? }`.
- `run`:
  - `LoadScenarioRequest { path, seed?, clock? }` (no tick-rate field, decision 9);
  - `StepRequest { count }` with `count` in 1..=1_000_000;

- `entities`:

- `components`: `ComponentEntry { kind, id, provenance?, version?, read_only?, param_schema? }`.
- `catalog`: `BehaviorCatalog { entries: [CatalogEntryDto { kind: node_type | condition | action | behavior,

### WebSocket stream (ADR 0027)
`GET /api/v1/stream?encoding=json`. The exchange:
1. The server sends `hello`, which includes the stream settings in force.
2. The client sends `subscribe { filter?: { bbox?, entity_ids?, event_kinds? }, max_rate_hz?, state_hash? }`.
   A missing `max_rate_hz` means `default_rate_hz`; a value above `max_rate_hz` is an `error`.
3. The server then sends `frame`s and, for bad client messages, `error`s. A frame carries `kind:
   "snapshot"`, `cause: "tick" | "control"`, `session`, `seq`, `tick`, `time_s`, `run`, `dropped`,
   `entities`, `events`, `events_truncated` and optionally `state_hash`.

Per connection:
- One engine `Subscription` (capacity `queue_frames`; `notify` = `tokio::sync::Notify`).
- A task that, whenever the socket is ready, drains the subscription, sends only the newest frame
  (filtered and converted), accumulates the skipped frames' events (at most `max_events_per_frame`), and
  then waits `1 / rate`.
- After `send_timeout_s`, the connection is closed with 1008 `too_slow`.

Filters and conversion never run on the engine thread. `#[doc(hidden)] Server::stream_stats()` exposes
per-connection queue maxima and drop counts for AT-10.

### Error model, versioning, determinism guarantees
- **Errors.** Problem details with the closed code list of ADR 0026. `HandleError`, `SessionError` and
  `ScenarioError` are mapped in one function (`umbra-server/src/problem.rs`); diagnostics travel as
  `DiagnosticDto`.
- **Versioning.** `/api/v1`, with `API_VERSION` in `info.version`, the status and `hello`. Changes within
  v1 are additive only; clients ignore unknown fields, enum values, event kinds and message types (ADR
  0026).
- **Determinism (REQ-K-4): the server must not perturb the simulation.**
  1. The handle drives the same `Kernel::tick` as `Engine::run`. Per-tick state hashes, intents and
     contacts of a handle-driven run equal an `Engine::run` of the same scenario, seed and clock mode,
     with any number of subscribers, slow or not (AT-5, gate 4).
  2. Commands apply between ticks in arrival order. The same command script applied at the same ticks
     gives the same hashes. That holds in stepped mode or while paused; in free-running modes the applied
     tick depends on arrival time and is reported (ADR 0024).
  3. Queries, frames and contract generation read through `&self`. There is no RNG draw and no
     wall-clock read outside `WallClock`; the engine thread's waits go through `Engine::pump`. Server
     pacing uses `tokio::time` and never reaches the engine.
  4. Every list is ordered (`EntityId`, `BTreeMap`); there is no `HashMap` iteration in server or engine
     code.
  5. Plugin fault state stays per session host (ASM-118).
  6. **Tick rate.** A scenario's explicit `tick_rate_hz` is never overridden. For a scenario that omits

     status and frames, and on stderr by `run` and `validate`. The same file under two configurations
     with different defaults gives different hashes, by design, and the report shows why (AT-17).

## Open questions (answered by the human, 2026-10-19: every recommendation accepted)
1. **Command access control (spec section 19 question 4).** Recommendation: not in v1. REQ-X-8 and spec
   1.3 already exclude it; the localhost default and scenario-root confinement limit the exposure; the
   single mutating-route layer keeps it cheap to add. Revisit at M8 (Windows app with remote engines).
2. **Online fetch.** May the build-engineer run one online `cargo fetch` in WI-1 for the server
   dependencies? Recommendation: yes, the same procedure as for `libloading` and `semver`.
3. **Default port.** Recommendation: `127.0.0.1:7878`. It can be changed with `--bind` or `[server] bind`;
   tests always use port 0.
4. **Duration.** Should a served run stop at the scenario's `duration_s`? Recommendation: yes
   (`stopped`, reason `duration`), as `umbra run` does. An "unbounded" load option can be added later,
   additively, if the GUI needs it.
5. **Scenario root default.** Recommendation: the working directory at startup, overridable with
   `--scenario-root` or `[server] scenario_root`. M5b's Playwright starts `umbra serve` from the
   repository root.
6. **Windows.** Confirm that M5 closes on the Linux gate only (NFR-3 unverified, as in M0-M4).
   Recommendation: yes. Nothing in the design is OS-specific beyond `tokio`'s own portability.
7. **Which commands read `umbra.toml`?** Recommendation: `run`, `validate`, `list-plugins` and `serve`,
   so that a defaulted tick rate gives the same `duration_ticks` everywhere. The alternative, `serve`
   only, keeps `run` free of an implicit file but makes `validate` and `serve` disagree for scenarios
   without a rate.
8. **Automatic discovery of `./umbra.toml`.** Recommendation: keep it, as decided, and log the file used.
   If you prefer no implicit input at all for `run`/`validate`, discovery can be limited to `serve`; then
   `run` reads only `--config`.
9. **REST tick-rate override.** Recommendation: none. A client wanting another rate edits or supplies
   the scenario; the server's configured default covers files without one.
10. **Config file `schema_version`.** Recommendation: optional (absent means 1), unlike scenario files.
    It is a hand-written deployment file, and a newer value is still rejected.

## Proposed assumptions (entered into `docs/assumptions.md` in WI-1 after acceptance)
- **ASM-149** Commands reach the engine "through the Ingest phase" (REQ-X-1) by being applied at the
  engine boundary right before the next tick. The kernel's Ingest phase stays reserved for network input
  (M6).
- **ASM-150** The snapshot bus of REQ-K-6 lives in `umbra-engine`, not the kernel (ASM-039). The kernel's
  Publish phase stays empty.
- **ASM-151** A served run starts paused at tick 0 (`ready`); `start` resumes it; it stops at the
  scenario's duration (`stopped`, reason `duration`).
- **ASM-152** Default limits, each configurable in `umbra.toml` where ADR 0029 lists it:
  - command queue: 64;
  - subscription capacity: 4;
  - real-time wait slice: 10 ms;
  - stream rate: 30 Hz, max 60;
  - events per frame: 4096;
  - send timeout: 10 s;
  - request body: 1 MiB;
  - page size: 100, max 1000;
  - step count: 1..=1,000,000.
- **ASM-153** API spawn builds a template exactly like a scenario placement without overrides or route.
  Names are unique among named entities (ASM-059). Spawned entities are `Owned`.
- **ASM-154** `POST /behaviors/validate` validates the posted document together with the session's other
  file graphs (re-read from disk, leaving out the one with the same graph ID) against the base + plugin
  registry. With no session, it validates against the base registry alone. Diagnostics of the other
  files are returned too.
- **ASM-155** Gate 4 gains `--test handle_determinism` (WI-9).
- **ASM-156** `umbra-server` uses `tokio::time` for stream pacing and timeouts. That is network output
  only, never the simulation. The workspace clippy bans stay as they are: no std `Instant`/`sleep` in the
  server.
- **ASM-157** Entity ids and ticks are JSON integers; JavaScript clients are exact below 2^53.
- **ASM-158** (human decision 2026-10-19) The default tick rate is 60 Hz (`DEFAULT_TICK_RATE_HZ`).
  - `[scenario] tick_rate_hz` is optional, and an explicit value always wins.
  - The default can be changed by `[simulation] tick_rate_hz` in `umbra.toml`, and by nothing else: no
    CLI or REST override.
  - `Scenario::tick_rate_source` records `scenario` or `default`.
  - The effective rate is a run input when defaulted, and it is reported in `SessionInfo`, status,
    frames, and on stderr by `run`/`validate`.
  - Whole hertz only (ASM-016 unchanged). `SCHEMA_VERSION` stays 1.
- **ASM-159** (human decision 2026-10-19) `umbra.toml`:
  - Location: `--config`, else `./umbra.toml`, else defaults. Relative paths resolve against the file's
    directory.
  - Read by `umbra-templates::config` with the located reader. Unknown keys are errors; all errors are
    reported.
  - Precedence: flag > file > default, per setting. Lists replace, they do not merge.
  - One `bind` socket-address key. `schema_version` is optional.
  - Read by `run`, `validate`, `list-plugins` and `serve`.
- **ASM-160** The `run`/`validate` stderr note about a defaulted tick rate is written regardless of
  `--log-level` (it is a reproducibility record, not a log line). Stdout is unchanged.
