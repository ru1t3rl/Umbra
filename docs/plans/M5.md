## Goal
The engine becomes controllable from another thread and over the network without changing what it
simulates. An `EngineHandle` owns one engine thread with at least 4 MiB of stack. That thread loads
scenarios, applies commands between ticks, and ticks by its clock. It publishes immutable frames to bounded
subscriptions that drop the oldest frame when full. Dropped events are carried over, and late
subscribers are primed with the current state.

The optional `umbra-server` crate puts two things on top of that handle and nothing else:
- a REST API under `/api/v1`, with OpenAPI generated by `utoipa`, committed and drift-checked;
- a WebSocket stream (JSON), with its schema committed.

Every path a load reads is confined to the scenario root, and requests are checked by `Host`. WebSocket
upgrades are also checked by `Origin`.

`umbra serve` starts the server. Deployment settings come from flags, an `umbra.toml` file, or built-in
defaults. Scenarios that omit `tick_rate_hz` run at a configurable default of 60 Hz, and that rate is
reported wherever the run is reported. Per-tick state hashes are identical with and without the server.

M5 is the contract that M5b's GUI consumes: the generated TypeScript client, the stream schema, and
stepped mode for Playwright. The contract is therefore designed for M5b now and changes only additively
afterwards.

### Default tick rate (human decision 2026-10-19; ADR 0010 note, ADR 0029)
```rust
// umbra-core (additive)
pub const DEFAULT_TICK_RATE_HZ: u32 = 60;
// umbra-templates (additive)
#[non_exhaustive] pub struct LoaderOptions { pub max_subgraph_depth: u32, pub default_tick_rate: TickRate /* 60 */ }
#[derive(Debug, Clone, Copy, PartialEq, Eq)] #[non_exhaustive]
pub enum TickRateSource { Scenario, Default }
// Scenario gains: pub tick_rate_source: TickRateSource   (tick_rate keeps holding the effective rate)
```
**Reader rule.**
- An absent `[scenario] tick_rate_hz` yields `LoaderOptions::default_tick_rate`, with
  `TickRateSource::Default`, and `duration_ticks` uses that rate.
- A present value is read exactly as today, with `TickRateSource::Scenario`.
- `read_settings` and `Reader::new` keep their signatures (check 2b).

**Precedence.**
1. An explicit scenario value.
2. Otherwise `[simulation] tick_rate_hz` from `umbra.toml`.
3. Otherwise 60.

No CLI flag and no REST field overrides a scenario's rate (decision 9).

**Visibility.**
- `SessionInfo`, `ScenarioInfo`, `GET /api/v1/status` and the frame `run` status report `tick_rate_hz` and
  `tick_rate_source`.
- Whenever the default applies, `umbra run` and `umbra validate` write this line to stderr:

**Registry.** The bus keeps `Mutex<Vec<Weak<Slot>>>`. `publish` copies the live `Vec<Arc<Slot>>` under the
lock and releases the lock before any push or `notify`. Poisoning is recovered with `into_inner`.

**Push rule.** Lock the slot, push the frame, and while `len > capacity` pop the front. Each popped frame
counts as a drop, and its events move to the carry buffer, up to `max_carry_events`, beyond which
`events_truncated` is set. Then unlock and call `notify`.

**Frame builds.**
- A tick frame is built only when `wants_frame(tick)` holds.
- Control frames are always built while any slot exists. So are the frames at a step's completion, at
  pause and at stop or duration.
- `state_hash` is computed only when a due slot asked for it.

**Engine thread loop** *(review: M3, M9, m2, M12, M1, M11, m16)*. This one thread is the only one that
touches an `Engine`.
```
loop:
  if shutdown flag: cancel pending step (reply Closed), drop session, exit
  serve "needs prime" slots: publish one Control frame of the current state to each, only to it
  for each queued command (try_recv), in arrival order:
      apply; if it changed state: publish a Control frame; then reply          // publish-then-reply
  if state is not running, or the clock is idle (paused, stepped with pending_steps() == 0):
      block on recv(); continue
  match session.engine_mut().pump(max_wait):
      Ticked(report) -> trace span `tick` with report.phase_wall (m16)
                        step_done := pending step and tick >= target
                        stop_now  := tick >= duration_ticks
                        publish a Tick frame if bus.wants_frame(tick) or step_done or stop_now (with report.events)
                        if stop_now: state := stopped(Duration)
                        reply the pending step: completed if step_done; completed=false if stop_now
      Aborted{report, fault} -> publish the faulting tick's frame (events kept); state := stopped(PluginFault);
                        reply the pending step: 409 step_cancelled
      Waited          -> continue                                              // wait slice checks the flag next turn
      Idle            -> block on recv()                                       // no spin
      Err(e)          -> state := stopped(Error); cancel pending step; publish a Control frame
  on channel disconnect: as the shutdown flag
```
- **Load (D-a).**
  1. Cancel the pending step (reply `step_cancelled`).
  2. Drop the old session.
  3. Run `Session::load`.
  4. On success, `ready`; on failure, `idle`.

  Either way, publish a Control frame, then reply.
- **Step (M10).**
  - Valid only in `running` with the stepped clock and no step pending; otherwise `StepInProgress`,
    `NotStepped` or `InvalidState`.
  - `stop` and the duration end the step with `completed: false`.
  - Pause, unload, a clock change away from stepped, and a fault reply `StepCancelled { reached }`.
- **States.** `stopped` and the duration stop are handle-level states; the clock itself is only paused.
- **Panics (m1).** A panic on the engine thread is not caught. The thread ends, every handle then gets
  `Closed`, and the server answers `503 engine_unavailable` from then on. The panic is logged.

### WebSocket stream (ADR 0027)
**Upgrade.** `GET /api/v1/stream?encoding=json`. Before upgrading, the server checks:
- `Origin` against `allowed_origins`: loopback origins on any port are always allowed, and an absent
  `Origin` is allowed;
- `encoding`;
- `max_connections`.

**Exchange.**
1. The server sends `hello`, carrying the protocol, `api_version`, `encoding` and the stream settings in
   force.
2. The client sends `subscribe { filter?, max_rate_hz?, state_hash? }`.
3. The server registers an engine `Subscription` with:
   - `capacity = queue_frames`;
   - `min_tick_stride = max(1, tick_rate_hz / max_rate_hz)`;
   - `max_carry_events = max_events_per_frame`.
4. That subscription is primed with a `cause: control` frame at once (M1).
5. The server sends frames and `error`s. There is no unsubscribe message; the client closes the socket.

**Connection structure** *(review: M4, m9)*. `run_connection<Si, St>(sink: Si, stream: St, ..)` is generic
over `Sink<Message>` and `Stream<Item = Result<Message, _>>`, and is split into two halves:
- **Reader task:** parses client messages. Messages over 64 KiB close the socket with 1009. More than
  10,000 `entity_ids` is an `error`. It updates the subscription.
- **Writer task:** waits on `notify` or the shutdown signal, then drains the subscription. Events come in
  order: `carried_events`, then the skipped frames' events, then the newest frame's. It filters, encodes on
  `spawn_blocking`, and sends only the newest frame, with `dropped` and `events_truncated`. It then waits
  `1 / rate`.

  A send is never cancelled mid-flight. If it exceeds `send_timeout_s`, the connection closes with 1008
  `too_slow`.

**Shutdown.** The server's shutdown signal makes both tasks close with 1001.

**Test probes.** `#[doc(hidden)] Server::stream_stats()` exposes per-connection queue maxima and drop
counts.

### CLI `serve`, `--config` (feature `server`, default on; ADR 0029)
```
umbra serve [--config FILE] [--bind ADDR] [--scenario PATH] [--clock MODE] [--seed N] [--start]
            [--scenario-root DIR] [--plugin-path DIR].. [--log-level L]
```
**Precedence and configuration.**
- Each setting resolves as flag > `umbra.toml` > default. `--config` works on every command.
- When `run`, `validate` or `list-plugins` uses an implicitly discovered `./umbra.toml`, it writes the
  stderr note `note: using configuration ./umbra.toml` *(review: m13)*.

**Startup and binding.**
- Default bind `127.0.0.1:7878`; port 0 picks a free port.
- Exactly one stdout line once bound: `listening on http://<addr>`.
- `--scenario` preloads the scenario. Its path is confined like a request; an absolute path given on the
  command line is accepted only if it is inside the root.
- A non-loopback bind warns, whether it comes from a flag or the config file.

**Shutdown** *(review: M12, m10)*. `umbra_server::run(config, handle, thread, shutdown: ShutdownMode)`
returns `Result<(), ServerError>`.
- `ShutdownMode` is either `Signals`, meaning `tokio::signal` for Ctrl-C and SIGTERM handled inside
  `umbra-server`, or `Manual(ShutdownSignal)`, a cloneable trigger used by tests.
- On shutdown the server takes these steps in order:
  1. Stop accepting connections.
  2. Call `EngineThread::shutdown`. The engine cancels pending steps, so their HTTP requests answer 503
     `engine_unavailable`.
  3. Signal the stream tasks, which close with 1001.
  4. Wait for in-flight requests, up to `shutdown_grace_s` (default 5 s).
  5. Drop the runtime.

**Exit codes.** 0 for a clean shutdown; 1 for a config, bind or preload failure; 2 for a usage error.

### Error model, versioning, determinism guarantees
- **Errors:** ADR 0026 (amended) code table, one status per code, mapped in `umbra-server/src/problem.rs`.
- **Versioning:** `/api/v1`, `API_VERSION`, additive only. Clients ignore unknown fields, enum values,
  event kinds and message types.
- **Determinism (REQ-K-4):**
  1. A handle-driven run has the same per-tick hashes, intents and contacts as `Engine::run` with any
     number of subscribers, of any speed or stride (AT-5, gate 4).
  2. Commands apply between ticks in arrival order, across all clients. A script applied at fixed ticks
     reproduces in stepped mode or while paused.
  3. Queries, frames, priming and contract generation read through `&self`. No RNG draws, and no
     wall-clock reads outside `WallClock`.
  4. Lists are ordered; no `HashMap` iteration.
  5. Plugin fault state is per session host.
  6. **Tick rate:** an explicit `tick_rate_hz` is never overridden, and a defaulted rate is a reported run
     input.
  7. **Publish-then-reply** *(review: M3)*: when any reply arrives, the frame reflecting it is already in
     every subscription.

## Acceptance tests for the test-engineer (step 4, write these first)
**How the tests run.**
- REST tests run in-process (`tower::ServiceExt::oneshot` on `Server::router`).
- Stream tests bind `127.0.0.1:0` and use `tokio-tungstenite`.
- The slow-client acceptance test drives the generic connection loop with a stub sink under
  `tokio::time::pause`.
- CLI tests run the built `umbra` binary in a temporary working directory.

**Assertions.**
- Failure assertions check the problem `code` and status, never message text.
- Engines use `ManualWallClock` unless a row says otherwise.
- No wall-clock duration is asserted.
- Tests that load real plugins follow the m8 rule: their own test file, or `PLUGIN_TEST_LOCK`.

## Risks (milestone level)
| Risk | Mitigation |
|---|---|
| New dependencies not in the offline cache; licence or advisory surprises; build time | One online `cargo fetch` in WI-1 before any code; the stop rule on licences and advisories |
| The server perturbs the simulation | Single engine thread; commands between ticks; `&self` reads; `pump` through `WallClock`; priming and strides only read. AT-5 in gate 4 |
| A slow client back-pressures the tick | Two bounded layers dropping the oldest frame; no consumer work on the tick thread; `notify` must not block; no registry lock held across push or `notify`. AT-3, AT-10 with a stub sink |
| The slow-client acceptance test cannot reach the blocked-send path over loopback *(review: M4)* | Generic connection loop tested with a `Pending` stub sink under paused time; one real-socket smoke with 2,000 entities |
| Events lost when frames are dropped *(review: M2)* | Carry-over buffer per slot, capped with `events_truncated`; AT-3, the AT-4 `step_100` row |
| Snapshot builds nobody reads cost tick time *(review: M11)* | Per-subscription `min_tick_stride` and `wants_frame`; the last state is always framed; AT-10 build-count probe |
| A late subscriber sees nothing until a tick *(review: M1)* | `Prime` on subscribe in every state; AT-4, AT-9 |
| A reply arrives before its frame *(review: M3)* | The publish-then-reply invariant in ADR 0024; AT-4 |
| Shutdown hangs on a full queue, a pending step or an open stream *(review: M12)* | Flag plus non-blocking wake; steps cancelled first; streams closed with 1001 on a signal; `shutdown_grace_s` deadline; `EngineThread` joins in `Drop`. AT-4 and AT-13 shutdown rows |
| An engine-thread panic | Not caught: permanent `503 engine_unavailable`, logged (ADR 0024 amendment); AT-4, AT-6 |
| Path escape through `..`, symlinks or scenario `plugin_paths` (native code) *(review: D-b)* | Lexical-then-canonical confinement of every input; 403 without an existence oracle; root-relative paths in responses. AT-19. TOCTOU between check and read accepted for a localhost server (ASM-162) |
| DNS rebinding or cross-site WebSocket from a browser *(review: D-b)* | `Host` allow-list layer; `Origin` check on upgrade; JSON-only bodies (415); AT-19 |
| Reloading the same plugin restarts its lifecycle *(review: D-a)* | Documented on `POST /scenario`; ADR 0021 RR-M1 reload is tested in M4; AT-4 `replace_with_same_plugin_without_unload` |
| A failed replacement load loses the old session *(D-a)* | By decision; documented; AT-6 `load_failure_leaves_idle_and_old_session_gone` |
| Same-process plugin tests interfere through the process-wide image table *(review: m8)* | Separate test files, or `PLUGIN_TEST_LOCK` |
| A scenario without `tick_rate_hz` depends on the configured default; a stray `./umbra.toml` is an implicit input | Explicit values win; the examples are explicit; rate, source and the implicit config file are reported on stderr and in the API |
| Frozen-milestone breakage (`tick_rate_hz` reader, kernel Events phase, `Kernel::remove`, shared spawn helper) | Additive only; check 2b over every touched file; `m2-compat.sh` after WI-2 and WI-4; proof items 1-5 |
| `validate` and `run` disagree under a config default | Both read the same config through `LoadSettings`; AT-17 |
| The config reader grows into a second TOML pipeline | It lives in `umbra-templates` on the existing reader (ADR 0029) |
| ABI drift during M5 | Explicit freeze; proof item 5; gate 11 |
| Stack overflow on the engine thread | 8 MiB default, under 4 MiB refused; AT-4 |
| Non-deterministic contract output | No `preserve_order`; sorted output; the generate-twice test |

## Open questions (answered by the human, 2026-10-19: every recommendation accepted)
1. **Command access control (spec section 19, question 4).** Recommendation: not in v1. REQ-X-8 and spec
   1.3 already exclude it; the localhost default and scenario-root confinement limit the exposure; the
   single mutating-route layer keeps it cheap to add. Revisit at M8 (Windows app with remote engines).
2. **Online fetch.** May the build-engineer run one online `cargo fetch` in WI-1 for the server
   dependencies? Recommendation: yes, the same procedure as for `libloading` and `semver`.
3. **Default port.** Recommendation: `127.0.0.1:7878`. It can be changed with `--bind` or
   `[server] bind`; tests always use port 0.
4. **Duration.** Should a served run stop at the scenario's `duration_s`? Recommendation: yes (`stopped`,
   reason `duration`), as `umbra run` does. An "unbounded" load option can be added later, additively, if
   the GUI needs it.
5. **Scenario root default.** Recommendation: the working directory at startup, overridable with
   `--scenario-root` or `[server] scenario_root`. M5b's Playwright starts `umbra serve` from the
   repository root.
6. **Windows.** Confirm that M5 closes on the Linux gate only (NFR-3 unverified, as in M0-M4).
   Recommendation: yes. Nothing in the design is OS-specific beyond `tokio`'s own portability.
7. **Which commands read `umbra.toml`?** Recommendation: `run`, `validate`, `list-plugins` and `serve`, so
   that a defaulted tick rate gives the same `duration_ticks` everywhere. The alternative, `serve` only,
   keeps `run` free of an implicit file but makes `validate` and `serve` disagree for scenarios without a
   rate.
8. **Automatic discovery of `./umbra.toml`.** Recommendation: keep it, as decided, and log the file used.
   If you prefer no implicit input at all for `run`/`validate`, discovery can be limited to `serve`; then
   `run` reads only `--config`. *(Amended after the design review, m13: the implicit file is also
   announced on stderr.)*
9. **REST tick-rate override.** Recommendation: none. A client wanting another rate edits or supplies the
   scenario; the server's configured default covers files without one.
10. **Config file `schema_version`.** Recommendation: optional (absent means 1), unlike scenario files. It
    is a hand-written deployment file, and a newer value is still rejected.

No new open questions came from the design review: every choice was decided as D-a, D-b, D-c or D-d.

## Assumptions (entered into `docs/assumptions.md` in WI-1)
- **ASM-149.** Commands reach the engine "through the Ingest phase" (REQ-X-1) by being applied at the
  engine boundary, right before the next tick. The kernel's Ingest phase stays reserved for network input
  (M6).
- **ASM-150.** The snapshot bus of REQ-K-6 lives in `umbra-engine`, not the kernel (ASM-039). The kernel's
  Publish phase stays empty.
- **ASM-151.** A served run starts paused at tick 0 (`ready`). `start` resumes it, and it stops at the
  scenario's duration (`stopped`, reason `duration`).
- **ASM-152.** Default limits, configurable where ADR 0029 lists them:

  | Limit | Default |
  |---|---|
  | Command queue | 64 (0 refused) |
  | Subscription capacity | 4 |
  | Real-time wait slice | 10 ms |
  | Stream rate | 30 Hz, max 60 |
  | Events per frame and carry-over cap | 4096 |
  | Send timeout | 10 s |
  | Shutdown grace | 5 s |
  | Request body | 1 MiB |
  | Incoming WebSocket message | 64 KiB |
  | `entity_ids` per subscribe | 10,000 |
  | Stream connections | 64 |
  | Page size | 100, max 1000 |
  | Step count | 1..=1,000,000 |
- **ASM-153.** An API spawn builds a template exactly like a scenario placement without overrides or
  route. Names are unique among named entities (ASM-059). Spawned entities are `Owned`.
- **ASM-154.** `POST /behaviors/validate` validates the posted document together with the session's other
  file graphs, against the session registry, on the engine thread and inside the plugin build scope
  (amended, M6). With no session it uses the base registry. Diagnostics of other files are returned too.
- **ASM-155.** Gate 4 gains `--test handle_determinism` (WI-10).
- **ASM-156.** `umbra-server` uses `tokio::time` for stream pacing, timeouts and the shutdown grace
  period. These affect network output only, never the simulation. Signal handling is `tokio::signal` in
  `umbra-server`.
- **ASM-157.** Entity ids and ticks are JSON integers, exact in JavaScript below 2^53. Seeds are decimal
  strings (D-c).
- **ASM-158.** (Human decision 2026-10-19.) The default tick rate is 60 Hz. An explicit
  `[scenario] tick_rate_hz` always wins. Only `[simulation] tick_rate_hz` can change the default. The
  source is recorded and reported. Whole hertz only; `SCHEMA_VERSION` stays 1.
- **ASM-159.** (Human decision 2026-10-19.) `umbra.toml`:
  - found via `--config`, else `./umbra.toml`, else built-in defaults;
  - read by `umbra-templates::config`, with strict keys and all errors reported;
  - precedence is flag > file > default, and lists replace rather than merge;
  - one `bind` key; `schema_version` optional;
  - read by `run`, `validate`, `list-plugins` and `serve`;
  - an implicitly discovered file is announced on stderr (m13).
- **ASM-160.** The stderr notes about a defaulted tick rate and an implicit config file are written
  regardless of `--log-level`. Stdout is unchanged.
- **ASM-161.** *(Review: D-a.)* A load drops the old session first. A failed load leaves `idle`. `Session`
  fields drop as engine, registry and behaviors, then host, so a reload with the same plugin starts a new
  image lifecycle. A validation-mode host reuses a live session image without `init`/`shutdown`.
- **ASM-162.** *(Review: D-b.)* Served loads are confined:
  - Request paths resolve against the scenario root and are checked lexically, then canonically. A
    missing path outside the root is `403`.
  - Template and graph files and `template_paths` must stay inside the root. `plugin_paths` must stay
    inside the root or the configured plugin paths.
  - Responses show only root-relative paths.
  - The TOCTOU race between the check and the read is accepted on a localhost server.
  - A future terrain that takes file paths (M7) must use the same check.
- **ASM-163.** *(Review: D-b.)* `Host` is allowed if it is loopback on any port, the bound address, or
  listed in `[server] allowed_hosts`. A WebSocket `Origin` is allowed if it is loopback on any port, listed
  in `[server] allowed_origins`, or absent. REST relies on the absence of CORS plus JSON-only bodies.
  Tauri origins come in M8.
- **ASM-164.** *(Review: m1.)* An engine-thread panic is not caught. It ends the thread, and the server
  answers `503 engine_unavailable` until restarted.
- **ASM-165.** *(Review: M11.)* The stream stride is `max(1, tick_rate_hz / max_rate_hz)`, using integer
  division. Frames are always built for control changes, step completion, pause and stop.
