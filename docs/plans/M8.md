## Goal
M8 turns the M5b live map into the full v1 GUI (spec section 13) and a Windows desktop app. It extends
the M5b app; it does not replace it.
1. **Dashboard.** An extended dashboard: live map with selection, run and clock controls, scenario
   loading, entity list and inspector, and a log.
2. **New pages.** Templates (parameter forms from JSON Schemas), plugins (plugins, capabilities,
   faults, network adapters, components) and settings.
3. **Windows app.** A Tauri 2 desktop app with a bundled `umbra` sidecar or a remote engine, behind a
   loopback gateway (same origin as the web build).
4. **No engine change.** M8 changes no engine crate, no `api/` file, no example and no engine acceptance
   criterion (ADR 0047). Contract gaps go to the engine side as requests (section "Contract gaps").

**Gate check (implement-milestone step 1, ADR 0047).** M5b is ticked, tagged `m5b-done` and merged.
ADR 0047 lets M8 start alongside M7. The M7-dependent work items (WI-24..WI-27), the acceptance run and
the `m8-done` tag wait for `m7-done`.

There is no CI (ADR 0004). The local gate list in `docs/build.md` is the definition of done. Gate 15
(`scripts/gates.sh --gui`) applies to every work item. The new opt-in Tauri step (ADR 0077) applies from
WI-19.

### Shell `route` metadata (WI-3)
`route = { path, label, icon, nav: boolean, lazy }`. `src/router.tsx` builds both the router and the
`NavItem[]` (only routes with `nav: true`) from the same list.
- **`src/components/App`.** It nests the providers of ADR 0074. A `NavigationBridge` component inside
  the router maps `useNavigate()` and `useLocation()` into `NavigationProvider`. The router root is a
  layout route whose element renders `NavigationBridge` and `<Outlet />`.
- **`src/components/SessionInvalidator`.** It runs `useInvalidateEngineQueries()` whenever
  `useRunStatus()?.session` changes. That is about five lines of wiring and the only new logic in
  `src` (ASM-851).

### Data flow
```
umbra serve --REST--> @umbra/data (orval hooks)  -> scenario-control, entity-inspector (detail),
                                                    template-browser, plugin-status
            --WS----> @umbra/engine-stream: decode -> journal.append(events, loss, run/session/connection)
                         -> pending slot (latest wins) -> rAF flush -> store {status, run, frame}
                                                        -> journal notify (same flush)
                         ├─ EntitySource (imperative) -> map-view (setData <= 1/frame; selection layer, label)
                         ├─ EntitySource + 4 Hz throttle -> entity-inspector EntityListPanel (VirtualList)
                         ├─ useEntity(selectedId) -> EntityInspector (one component, per flush)
                         ├─ useRunStatus -> scenario-control (RunStatusBar, RunControls, RunFaultAlert)
                         └─ JournalSource (imperative) -> log-view (VirtualList role=log)
desktop only: src-tauri sidecar stdout/stderr -> event engine_output -> @umbra/desktop -> log-view
```
- **Query freshness.**
  - `SessionInvalidator` invalidates all engine queries on a session change.
  - The inspector refetches its entity detail every 1 s while running, and after each control frame
    (ASM-806).
  - Plugin status refetches on run-state change and polls adapters every 2 s while running (ASM-821).
- **Subscription.** `useApplySubscription({ max_rate_hz: settings.stream.maxRateHz })` is called once
  by the dashboard shell. The viewport `bbox` filter stays off in M8 (ASM-861).

### Performance plan (10,000 entities)
1. The M5b pipeline is unchanged: one store notification per flush and `setData` at most once per
   animation frame.
2. The entity list subscribes imperatively. It rebuilds its row model (sorting by id is already the
   frame order, plus the filter) at most every 250 ms, and renders only the visible rows (ADR 0072).
   - Test: `EntityListPanel` renders at most `visible + 2*overscan` rows for 10,000 entities.
   - Test: its render count over 100 frames in 1 s is at most 5.
3. The inspector re-renders once per flush for one entity. The lookup is a binary search by id in the
   frame (ids ascending), O(log n).
4. **Selection on the map.**
   - The ring is drawn by a one-feature GeoJSON source, updated in the same flush.
   - The label is one DOM node, moved by `transform` per flush.
   - Hit testing runs only on click.
5. The journal appends in O(events). The log view renders only its visible rows. Test: 50,000 records,
   render count constant while 1,000 records per second arrive (fake scheduler).
6. Measured, not gated (running log, WI-14):
   - flush time at 10,000 entities with the list, inspector and selection mounted;
   - list rebuild time;
   - the gateway's added latency for a 10,000-entity frame (WI-20).
7. Escalation: if the dashboard flush exceeds 16 ms on the reference machine, first the Worker decoder
   (ADR 0045 option 3), then the bbox subscription. Either needs a new ADR in the 0079+ block.

**H-1 Parameter forms (ADR 0070, D-80).** An own read-only renderer in a new foundation package
`@umbra/schema-form` over a documented JSON Schema subset, with a JSON fallback. The alternatives are
`@rjsf/core` with a Vantage theme and JSON Forms.

**H-2 Desktop transport (ADR 0075, D-85).** Three choices:

- (b) engine-side CORS plus the Tauri origins: an engine change and gap G-3, requested from the M7
  side;
- (c) Tauri HTTP and WebSocket plugins behind injected transports.
- **Rec: (a).**

**H-3 Windows bundle (ADRs 0076, 0077, D-86, D-87).**

- Identifier `org.umbra.desktop`.
- **Rec: NSIS, `embedBootstrapper`, unsigned, bundle the examples, identifier as proposed.** Say
  `offlineInstaller` if the target machines have no internet at install time.
