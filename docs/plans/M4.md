## Goal
Native plugins drive entities. A plugin is a dynamic library built with `umbra-sdk` (Rust) or against the
generated `umbra_plugin_api.h` (C), exporting only `umbra_plugin_entry`. The host loads it from plugin
directories, checks `plugin.toml` and the ABI version before and after opening it, validates the
descriptor, and registers each `behavior` capability in the one registry (D-8) with `Provenance::Plugin`.
From then on a plugin behavior is used exactly like a registered behavior: as a template `[behavior] ref`
and as a `subgraph` target with bound inputs and outputs. Top-level plugin behaviors are ticked in
batches (REQ-B-4), with time passed in the call and randomness only from the entity's hashed stream via
the host API (REQ-K-4). Every FFI boundary has panic guards; faults follow `on_plugin_fault`.

**Acceptance (spec section 17, M4):**
1. Example plugin loaded and driving entities (AT-8, AT-7).
2. All plugin failure tests pass (AT-4, gate 13).
3. A C example compiles against the header (AT-9, and AT-2 for the header itself).

**Gate check (step 1):** M3 is ticked in `docs/milestones.md` with evidence (tag `m3-done`, full local gate
on Linux at `eebc70f`, 1499 tests). The rename (ADR 0018) is done (`umbra-rename`) and WI-R4 applied A-002

## Compatibility (A-001 freeze; M3 kept)
M0-M2 are frozen (additive only); M3 is not frozen but every M3 test and golden value must keep passing.
### What changes in existing crates, and why it is additive
- `umbra-core` (M0-frozen): new default methods only (`Behavior::batch`, `BehaviorInstance::as_any_mut`),
  new items (`BehaviorBatch`, `BatchItem`, `tick_each`, `PluginFaultPolicy`). No existing signature,
  variant or field changes. Every existing `Behavior`/`BehaviorInstance` impl compiles unchanged.
- `umbra-kernel`: the private `BehaviorSlot` gains a field; the Behavior phase gains a grouped path taken
  only when `Behavior::batch()` is `Some`. No public item changes; behaviors without a batch run the M3
  code path.
- `umbra-templates`: `Scenario` (never built literally by M2/M3 tests) gains `plugin_paths` and
  `on_plugin_fault`; new reader keys `plugin_paths`, `on_plugin_fault`; `scenario.v1.schema.json` gains two
  optional properties; one new pub function. `plugins` stays an unknown key, so the M2 tests
  `unknown_key_in_the_scenario_table_is_unknown_key` and the fixture `unknown_scenario_key.toml` pass as
  they are (ADR 0022). `SCHEMA_VERSION` stays 1.
- `umbra-engine`, `umbra-cli`: new functions, re-exports, `#[non_exhaustive]` enum variants
  (`EngineError::PluginFault`, `ScenarioError::Plugin`), a new flag and (if approved) a new command. Structs
  that tests build literally (`EngineConfig`, `RunOptions`, `SpawnSpec`, `RouteSpec`, `EntityInit`,
  `RouteInit`, `KernelConfig`) get **no** new fields; plugins are attached with `Engine::attach_plugins`.
  `standard_registry()` and `builtin_registry()` keep their contents (no plugins).
- No M0-M3 test, fixture or golden file is edited. No `#[ignore]` is added to an existing test.

### `umbra-plugin-api` (ADR 0019, ADR 0020, ADR 0021)
Rust source is the single truth; cbindgen generates the C header. Every function-pointer field is `Option`
(ADR 0019). "hdr" below = the two leading fields `abi_version: u32, struct_size: u32`.

Intent field use (ADR 0016 set v1; unused fields zero/empty and ignored):
| Kind | Fields | Core variant |
|---|---|---|
| `MOVE_TO` | `position` (ECEF) | `MoveTo { destination }` |
| `FOLLOW_ROUTE`, `HOLD`, `DESPAWN` | none | as named |
| `SET_SPEED` | `value` (m/s) | `SetSpeed` |
| `SET_HEADING` | `value` (rad, true heading) | `SetHeading` |
| `FIRE` | `entity` (target, non-zero), `id` (`WeaponId`) | `Fire` |
| `SPAWN` | `id` (`TemplateId`), `position`, `value` (heading rad) | `Spawn` |
| `CUSTOM` | `id` (`ComponentId`), `payload` (JSON) | `Custom` |
An unknown kind, a zero `Fire` target, an ID that fails ADR 0002, or a payload that is not JSON is
refused by the sink with `UMBRA_ERR_INVALID_ARGUMENT` and faults the capability (ADR 0021). Non-finite
numbers pass through as in core (motion ignores them, ASM-048).

Behavior `metadata` JSON (ADR 0020): `{"param_types": {"<param>": "bool|number|integer|string|entity|position"},
"outputs": {"<port>": "<bbtype>"}, "result": "<text>"}`, every key optional, unknown keys rejected.

### `umbra-kernel` changes (private)
`BehaviorSlot` gains `batch: Option<Arc<dyn BehaviorBatch>>`, set at `spawn_with` from `behavior.batch()`.
Behavior phase (ADR 0020): (1) for each entity in id order: clear intents; Remote: stop; no slot: M1
stand-in; slot without batch: tick as in M3 and post-process; slot with batch: append to its group
(groups found with `Arc::ptr_eq`, ordered by first entity id). (2) Each group, in order: build one
`BatchItem` per member (id order) over that entity's own view, RNG stream, intent buffer and instance, call
`tick_batch` once, write `last` status. (3) Post-process the batched entities in id order
(`expand_follow_route`). Scratch vectors are kept in the world and reused (no per-tick allocation once

Bridge (private): `PluginFactory` (`Factory<dyn Behavior>`: `build` = `configure`, panics and errors become
`BuildError`), `PluginBehavior` (`Behavior`: `instantiate`, `batch()` returns the capability's shared
`Arc<CapabilityBatch>`), `PluginInstance` (`BehaviorInstance`: `tick` = batch of one, `halt`,
`halt_running` (vtable entry or `halt`), `set_input`/`output` through `UmbraValue`, `as_any_mut`),
`CapabilityBatch` (`BehaviorBatch`: marshals all items into reused scratch `UmbraEntityView`/`UmbraContact`/
`UmbraBehaviorItem` buffers, one `tick_batch` call, converts intents with ID and JSON checks). Every handle
holds `Arc<LoadedPlugin>`; `LoadedPlugin::drop` calls `shutdown` and then closes the library, so unload
follows the last handle (REQ-P-8). All calls into one plugin go through its `Mutex` (ADR 0019 threads
rule; this is what makes the `unsafe impl Send/Sync` of the handle types sound). A faulted capability is
an `AtomicBool` on the capability; the fault board is shared by the host and every bridge object.
Interface mapping: `metadata` and schema -> `ComponentInfo::new(schema description, Provenance::Plugin,
version).with_param_type(..).with_output(..).with_result(..)`, checked for consistency (ADR 0020).

## Risks (milestone level)
| Risk | Mitigation |
|---|---|
| A layout or convention mistake frozen by REQ-P-2 | ADR 0019/0020 approved before WI-3; layout pin tests and C `_Static_assert`s; reviewer checks field by field; ABI is 0.0 with no external users yet |
| Undefined behavior at the boundary (null function pointers, invalid enums or `bool`, dangling views) | ADR 0019 rules (`Option` function pointers, integer enums, `u8` booleans, call-scoped pointers); validation before use; tests for each row |
| A panic unwinds across FFI | `catch_unwind` in every SDK export and host callback; Rust's abort-on-unwind at `extern "C"` as the backstop; panic test per callback |
| Determinism broken by plugins or by batching | Host RNG only, time in calls, deterministic load and call order, group order by first id; equivalence tests (AT-6), plugin determinism gate and 4-process test (AT-7) |
| M3 behavior or golden hashes move | Batched path only when `batch()` is `Some`; compatibility proof items 1-4; gate 4 unchanged targets |
| `dlclose` of a Rust cdylib with thread-locals crashes at exit (macOS, sometimes Linux) | Unload-ordering tests; fallback (needs an ADR amendment): keep libraries loaded until process exit, still calling `shutdown` |
| Windows loading and MSVC compilation never run (NFR-3) | Platform-neutral code paths (`DLL_EXTENSION`, absolute paths, `cc`); recorded as unverified unless the human provides a Windows run |
| Missing prerequisites (`cbindgen`, C compiler) or offline `cargo fetch` for `libloading`/`cc` | WI-1 checks and pins; `docs/build.md` prerequisites; xtask exit 2 with the install line |
| Test time and flakiness from building plugin libraries inside tests | One helper, one target dir per test binary, `OnceLock`, `--offline --locked`; time recorded in WI-10 |
| The `unsafe_code` lint assumption behind ADR 0023 item 5 is wrong | WI-2 spike before any plugin crate |
| Soundness of `unsafe impl Send/Sync` for bridge handles | Per-plugin mutex serialises every call; `// SAFETY:` and a two-thread test |
| Scope creep into other kinds or a richer host API | Out-of-scope list; kind numbers reserved only; ADR 0021 staging |
