# ADR 0023: Plugin tooling, crates and supply chain

- **Status**: Accepted (human project owner, 2026-10-18; proposed by the architect in the M4 plan `docs/plans/M4.md`).
  Item 5 (CLAUDE.md rule 5 / NFR-2 narrow exception) is accepted conditionally: it applies only if the WI-2 lint
  test confirms that `unsafe_code` fires on the `export_plugin!` expansion; otherwise it is dropped and
  `forbid(unsafe_code)` stays. CLAUDE.md rule 5 is amended only after WI-2 confirms.
- **Requirement IDs**: REQ-SDK-2, REQ-SDK-3, REQ-P-1, REQ-A-1..3, NFR-2, NFR-3, NFR-4, D-6, D-19, ADR 0001,
  ADR 0004, ASM-002, ASM-005, ASM-009, ASM-020, ASM-024
- **Affected**: root `Cargo.toml`, `deny.toml`, `xtask` (rule table, unsafe check, `gen-header`,
  `build-plugins`), `docs/build.md`, `CLAUDE.md` rule 5, `umbra-plugin-host`, `umbra-sdk`, plugin crates

## Context
M4 activates gates 11-13 (`docs/build.md`): header drift, plugin build, plugin failure matrix. Loading
needs `dlopen`/`LoadLibraryW`; the header is "generated by `cbindgen`" (REQ-SDK-2, section 4); the
acceptance needs "a C example compiles against the header"; plugin tests need real libraries built from
Rust. Constraints: `cargo deny` allows only MIT, Apache-2.0, Unicode-3.0, Zlib (ASM-020) and denies
copyleft; `cbindgen` is MPL-2.0. `export_plugin!` must emit `#[unsafe(no_mangle)] extern "C" fn
umbra_plugin_entry`, and the `unsafe_code` lint fires on `no_mangle` in the crate where the macro expands,
so every SDK-built plugin crate (the example, the test fixture, every third-party plugin) cannot carry
`#![forbid(unsafe_code)]`, which ASM-024 requires outside the three FFI crates.

## Options and decision (one row per question; recommended option first)
1. **Library loading**: (a) `libloading` (ISC; tiny, cross-platform, `Library::new`/`get`) and add `ISC`
   to `deny.toml` in that PR; (b) hand-written `dlopen`/`LoadLibraryW` declarations (no dependency, more
   `unsafe` and platform code). **Chosen: (a).**
2. **Header generation**: (a) `cbindgen` as an installed tool pinned like cargo-deny
   (`cargo install --locked cbindgen@<pinned>`), run by `cargo xtask gen-header [--check]`, which refuses a
   different `cbindgen --version`; config `crates/umbra-plugin-api/cbindgen.toml` (C11, `cpp_compat`,
   include guard `UMBRA_PLUGIN_API_H`, SPDX header per ADR 0001); output committed at
   `crates/umbra-plugin-api/include/umbra_plugin_api.h`. MPL-2.0 never enters `Cargo.lock`; (b) `cbindgen`
   as an `xtask` library dependency with a per-crate MPL-2.0 exception in `deny.toml` (version pinned in
   the lockfile, but a copyleft exception and about 15 more crates). **Chosen: (a)** (ASM-009 already puts
   it in `xtask`, not a `build.rs`).
3. **C example**: (a) `examples/plugins/c-circle/plugin.c` is compiled with `-std=c11 -Wall -Wextra
   -Werror -pedantic` (MSVC `/W4 /WX`) into a shared library and loaded by a host test that ticks an
   entity, using the `cc` crate (MIT OR Apache-2.0) as an `umbra-plugin-host` dev-dependency, and packaged
   by `xtask build-plugins` (also `cc`); a C compiler becomes a prerequisite of the local gate (on Windows
   the MSVC Build Tools that the Rust MSVC toolchain already needs); (b) compile only, in gate 12, without
   loading it. **Chosen: (a)**; it proves the header and the Rust layout agree from the C side.
4. **Crates and members**: new crates `umbra-plugin-api` (`no_std`, no dependencies), `umbra-plugin-host`
   (core, plugin-api; `libloading`, `toml`, `serde_json`, `thiserror`, `tracing`), `umbra-sdk`
   (plugin-api; `serde_json`, `thiserror`), all already in the rule table. Also workspace members: the
   example `examples/plugins/wander` (package `example-wander`, explicit member entry) and the test fixture
   `crates/umbra-test-plugin` (a cdylib built with the SDK, not in section 4, recorded here). Rule-table
   entries: both may depend on `umbra-sdk` only (REQ-SDK-3). Tests that need a library build it with
   `cargo build --locked --offline -p <pkg> [--features ..] --target-dir <CARGO_TARGET_TMPDIR>/plugins`
   once per test binary (one helper file shared with `#[path]`), so gate 3 stays self-contained.
5. **`unsafe` in SDK-built plugin crates**: (a) plugin crates (the two above; third parties likewise) use
   `#![deny(unsafe_code)]` at the root; `export_plugin!` carries its own `#[expect(unsafe_code)]` on the
   one generated item; `xtask check-deps` gains a plugin-crate class that requires `deny(unsafe_code)` and
   rejects any `unsafe` token in their sources (parsed with `syn`), so the macro expansion is the only
   unsafe; CLAUDE.md rule 5 and NFR-2 get this one exception; (b) add the plugin crates to `UNSAFE_ALLOWED`
   (weaker: hand-written unsafe allowed); (c) no Rust plugin crates (contradicts REQ-SDK-3). **Chosen: (a).**

## Consequences
- Easier: offline, scripted gates on both OSes; the header and the C example prove the ABI from C;
  plugin crates show that SDK users need no hand-written `unsafe`.
- Harder: two more prerequisites (`cbindgen`, a C compiler); first test run builds plugin libraries
  (target: under a minute, measured in WI-10); `ISC` joins the licence allow-list.
- Revisit if `cbindgen` output drifts across patch versions (pin tighter), if Windows loading needs
  `LoadLibraryExW` flags beyond `libloading`, or if `cc` cannot find a compiler on a supported machine.
