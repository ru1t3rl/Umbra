# ADR 0025: Server stack and contract generation

- **Status**: Accepted by the human 2026-10-19 (proposed by the architect, M5 plan `docs/plans/M5.md`; awaiting the human project owner; needs one
  online `cargo fetch`)
- **Requirement IDs**: REQ-X-4, REQ-X-6, REQ-X-7, REQ-A-1..4, D-10, D-11, D-12, NFR-4, NFR-6, ASM-002, ASM-008, ASM-020
- **Affected**: `umbra-api-types`, `umbra-server`, `umbra-cli`, `xtask`, `deny.toml`, `Cargo.lock`,
  `api/`, skill `update-openapi`

## Context
D-11 fixes REST with OpenAPI generated by `utoipa` plus a WebSocket stream; D-12 fixes a separate wire
types crate; section 4 names `axum`. REQ-X-4 needs the OpenAPI document served and committed with a drift
check (gate 10); REQ-X-6 needs the stream message types exported as JSON Schema and documented with
AsyncAPI, and the GUI generates its TypeScript types from those files (`gui/CLAUDE.md` rule 7, skill
`generate-api-client`). None of `axum`, `tokio`, `hyper`, `tower`, `utoipa` or `tungstenite` is in the
offline cargo cache (checked 2026-10-19). `xtask` depends on no workspace crate (ASM-002). The
`update-openapi` skill text mentions `schemars` and Rust-side TS derives.

## Options
1. **axum + tokio + utoipa only; stream schema derived from the same `utoipa` schemas (chosen).** One
   derive (`serde` + `utoipa::ToSchema`) per wire type; the stream JSON Schema (2020-12) is built from the
   OpenAPI 3.1 component schemas of the stream types with `$ref`s rewritten to `$defs`; TypeScript comes
   from the JSON files in `gui/` (no Rust TS derive). Pros: one source of truth, fewest dependencies.
   Cons: a small schema-rewriting function to maintain.
2. **axum + utoipa + `schemars` (+ `ts-rs`)**, as the skill text says. Cons: two schema derives that can
   disagree on the same type; extra dependencies; Rust-side TS output duplicates `bun run gen:api`.
3. **Hand-written OpenAPI.** Cons: drifts from the code; contradicts D-11.

## Decision
Option 1.
- **Crates.** `umbra-api-types`: DTOs only; external deps `serde` (derive) and `utoipa` (derive), no
  workspace deps (rule table unchanged, ASM-008). `umbra-server`: `axum` (features `http1`, `json`,
  `query`, `ws`, `tokio`), `tokio` (`rt-multi-thread`, `net`, `sync`, `time`, `macros`, `signal`),
  `utoipa`, `serde`, `serde_json`, `thiserror`, `tracing`, `futures-util` (if `axum` needs it for
  `ws` split); workspace deps `umbra-engine`, `umbra-api-types` only (existing rule entry). Dev:
  `tokio-tungstenite` (client side of tests), `tower` (`util`, `oneshot`). `umbra-cli` gains an optional
  dependency on `umbra-server` behind a default-on feature `server`; `tungstenite` (sync client) as a
  dev-dependency for process tests. The engine crates gain no new dependency.
- **Versions** are the current releases at fetch time, pinned in `Cargo.lock` (build-engineer, WI-1);
  `cargo deny check` and `cargo audit` must pass. Expected licences: MIT, Apache-2.0, `MIT OR
  Apache-2.0`, and **BSD-3-Clause** (`matchit`, the axum router, is `MIT AND BSD-3-Clause`), which is
  added to `deny.toml` with a note (ASM-020). Anything else stops WI-1 for a decision.
- **Runtime.** `umbra-server` owns the tokio runtime (`umbra_server::run(config, handle, shutdown)` is
  blocking and builds a multi-thread runtime with 2 workers), so `umbra-cli` needs no tokio dependency.
  Wall time in the server (rate limiting, send timeouts) uses `tokio::time` and never reaches the
  simulation (ASM-013 scope: the clippy bans stay; the server uses no banned std item).
- **Generated files** (committed, LF, pretty JSON, trailing newline): `api/openapi.json` (OpenAPI 3.1,
  `info.version` = the API version constant, not the crate version), `api/stream.schema.json` (`$id`
  `urn:umbra:schema:stream:v1`, ADR 0018 C4), `api/asyncapi.json` (AsyncAPI 3.0, channel `/api/v1/stream`,
  messages referencing the stream schema). They are produced by `umbra_server::contract::documents()`
  and printed by the example target `crates/umbra-server/examples/gen_api.rs`.
- **Drift gate.** `cargo xtask gen-api [--check]` runs `cargo run --locked --offline -q -p umbra-server
  --example gen_api` and writes or compares the three files (LF-normalised), exit 0 current/written, 1
  drift, 2 usage, build or I/O error; `xtask` keeps no workspace dependency (ASM-002 unchanged). The
  served `/api/v1/openapi.json` is the same `documents()` output (test). Output order is deterministic
  (paths and schemas sorted; checked by generating twice).
- **Skill.** `update-openapi` step 1 is corrected to "`serde` + `utoipa::ToSchema` derives; no `schemars`,
  no Rust TS derive" (docs change in the plan's docs WI).

## Consequences
- Easier: one derive per DTO; `bun run gen:api` reads three committed files; no runtime in the engine.
- Harder: the dependency tree grows by roughly 60-80 crates (build time, audit surface); one online fetch
  by the human; `BSD-3-Clause` enters the allow-list; the `$ref` rewrite must follow `utoipa` output.
- Revisit if `utoipa` stops emitting JSON-Schema-compatible 3.1 schemas, if msgpack encoding is added
  (`rmp-serde`, a later ADR), or if TLS or auth is needed (non-goal in v1).
