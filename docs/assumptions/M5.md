## M5 Engine handle, control API and stream (recorded 2026-10-19 by architect, plan `docs/plans/M5.md`; entered by the build-engineer in WI-1; ASM-149..165 are copied from the plan's Assumptions section, ASM-166 and ASM-167 originate here)

Plan, ADRs 0024-0029 and the design-review amendments accepted by the human 2026-10-19. The authoritative wording of each entry is in the plan's "Assumptions" section.

| ID | Assumption | Reason | Revisit when |
|---|---|---|---|
| ASM-149 | Commands reach the engine "through the Ingest phase" (REQ-X-1) by being applied at the engine boundary, right before the next tick. The kernel's Ingest phase stays reserved for network input (M6). | Keeps the kernel unchanged and the tick order fixed (REQ-K-4). | M6 network input |
| ASM-150 | The snapshot bus of REQ-K-6 lives in `umbra-engine`, not the kernel (ASM-039). The kernel's Publish phase stays empty. | The kernel stays synchronous and free of subscription policy. | A second consumer of the bus |
| ASM-151 | A served run starts paused at tick 0 (`ready`). `start` resumes it, and it stops at the scenario's duration (`stopped`, reason `duration`). | Clients subscribe before the first tick. | The GUI needs auto-start |
| ASM-152 | Default limits (configurable where ADR 0029 lists them): command queue 64 (0 refused); subscription capacity 4; real-time wait slice 10 ms; stream rate 30 Hz, max 60; events per frame and carry-over cap 4096; send timeout 10 s; shutdown grace 5 s; request body 1 MiB; incoming WebSocket message 64 KiB; `entity_ids` per subscribe 10,000; stream connections 64; page size 100, max 1000; step count 1..=1,000,000. | Conservative values that bound memory and wall time per client. | Measured load (M9) |
| ASM-153 | An API spawn builds a template exactly like a scenario placement without overrides or route. Names are unique among named entities (ASM-059). Spawned entities are `Owned`. | Same code path as the loader. | Spawn with overrides (later, additive) |
| ASM-154 | `POST /behaviors/validate` validates the posted document together with the session's other file graphs, against the session registry, on the engine thread and inside the plugin build scope (amended, M6). With no session it uses the base registry. Diagnostics of other files are returned too. | Plugin behaviors must resolve exactly as in a run. | Graph file CRUD (REQ-X-12) |
| ASM-155 | Gate 4 gains `--test handle_determinism` (WI-10). | Per-tick hashes must be identical with and without the server. | Never |
| ASM-156 | `umbra-server` uses `tokio::time` for stream pacing, timeouts and the shutdown grace period. These affect network output only, never the simulation. Signal handling is `tokio::signal` in `umbra-server`. | The wall-clock bans stay for simulation crates (ASM-013). | A runtime other than tokio |
| ASM-157 | Entity ids and ticks are JSON integers, exact in JavaScript below 2^53. Seeds are decimal strings (D-c). | `u64` seeds can exceed 2^53. | Ids approach 2^53 |
| ASM-158 | (Human decision 2026-10-19.) The default tick rate is 60 Hz. An explicit `[scenario] tick_rate_hz` always wins. Only `[simulation] tick_rate_hz` can change the default. The source is recorded and reported. Whole hertz only; `SCHEMA_VERSION` stays 1. | A defaulted rate is a determinism input. | Fractional rates |
| ASM-159 | (Human decision 2026-10-19.) `umbra.toml` is found via `--config`, else `./umbra.toml`, else built-in defaults; read by `umbra-templates::config` with strict keys and all errors reported; precedence is flag > file > default, lists replace rather than merge; one `bind` key; `schema_version` optional; read by `run`, `validate`, `list-plugins` and `serve`; an implicitly discovered file is announced on stderr (m13). | Server settings need a file; existing commands keep their stdout. | Per-user config locations |
| ASM-160 | The stderr notes about a defaulted tick rate and an implicit config file are written regardless of `--log-level`. Stdout is unchanged. | Stdout stays byte-identical. | Never |
| ASM-161 | (Review: D-a.) A load drops the old session first. A failed load leaves `idle`. `Session` fields drop as engine, registry and behaviors, then host, so a reload with the same plugin starts a new image lifecycle. A validation-mode host reuses a live session image without `init`/`shutdown`. | Plugin image lifecycle must be deterministic. | Multiple sessions |
| ASM-162 | (Review: D-b.) Served loads are confined: request paths resolve against the scenario root and are checked lexically, then canonically (a missing path outside the root is `403`); template and graph files and `template_paths` stay inside the root; `plugin_paths` stay inside the root or the configured plugin paths; responses show only root-relative paths; the TOCTOU race between check and read is accepted on a localhost server; a future terrain that takes file paths (M7) must use the same check. | NFR-6 on a network-reachable loader. | A non-localhost deployment |
| ASM-163 | (Review: D-b.) `Host` is allowed if it is loopback on any port, the bound address, or listed in `[server] allowed_hosts`. A WebSocket `Origin` is allowed if it is loopback on any port, listed in `[server] allowed_origins`, or absent. REST relies on the absence of CORS plus JSON-only bodies. Tauri origins come in M8. | DNS-rebinding and cross-site WebSocket defence without auth. | Auth or CORS is added |
| ASM-164 | (Review: m1.) An engine-thread panic is not caught. It ends the thread, and the server answers `503 engine_unavailable` until restarted. | A panic mid-tick leaves the world in an unknown state. | Supervised restart |
| ASM-165 | (Review: M11.) The stream stride is `max(1, tick_rate_hz / max_rate_hz)`, using integer division. Frames are always built for control changes, step completion, pause and stop. | Deterministic, wall-clock-free frame pacing. | Delta frames |
| ASM-166 | (M5 WI-1.) Dependency pins and the licence stop rule. (a) Direct server dependencies are `[workspace.dependencies]` minimum versions; exact resolved versions live in `Cargo.lock`. (b) There is no age rule for dependencies: ADR 0025 says "current releases at fetch time". At fetch time (2026-10-19) `tokio` 1.54.0, `hyper` 1.12.0 and `smallvec` 1.16.3 were same-day or days-old releases, and were pinned one release back (`tokio` 1.53.2, `hyper` 1.11.1, `smallvec` 1.16.2) under a coordinator instruction that has since been dropped; they stay as they are. (c) `utoipa` 6.0.0 (with `utoipa-gen` 6.0.1) is used per the human decision of 2026-10-19, taken before any contract exists; the feature set is `macros` only (never `preserve_order`). `tokio-tungstenite`/`tungstenite` 0.29.0 match axum 0.8.9, so the tree has one `tungstenite`. (d) Stop-rule interpretation: a licence expression that offers an allowed alternative (`OR`) does not trigger the "licence outside the set" stop. Such crates in the M5 tree: `ryu` `Apache-2.0 OR BSL-1.0`; `r-efi` `MIT OR Apache-2.0 OR LGPL-2.1-or-later`; `wit-bindgen`, `wasi`, `wasip2` `Apache-2.0 WITH LLVM-exception OR Apache-2.0 OR MIT`. A conjunction (`AND`) needs the licence on the list: `matchit` `MIT AND BSD-3-Clause`. | Supply-chain caution (NFR-4), one `tungstenite`, and a stop rule that cannot fire on a dual licence. | Dependency upgrade WIs; a later utoipa major (contract-drift review) |
| ASM-167 | (M5 WI-1.) `umbra-api-types` exports `API_VERSION = "1.0.0"` and `umbra-server` exports `API_BASE = "/api/v1"` as the scaffold's first contract (each with one test); `umbra-cli` has feature `server` (default on) enabling `dep:umbra-server`, with no `serve` command until WI-17. | Smallest real contract per crate (add-crate step 6). | WI-11, WI-17 |
| ASM-168 | (M5 WI-2.) Default tick rate details. (a) `umbra_core::DEFAULT_TICK_RATE_HZ = 60` and `impl Default for TickRate`; `LoaderOptions::default_tick_rate` and `umbra_engine::LoadSettings::default_tick_rate` default to it. (b) The reader gets the default through a `pub(crate)` field of `Reader` (set by the loader), so `Reader::new` and `read_settings` keep their signatures (m2-compat check 2b). (c) `ValidationReport` gains `defaulted_tick_rates: Vec<(PathBuf, TickRate)>`: the valid scenario files that omitted the key, sorted; a scenario with other errors is not listed. The CLI prints one stderr line per entry: `note: <path>: `tick_rate_hz` is not set; using the default of N Hz`. (d) `load_scenario_with_plugins_and_settings` and `validate_path_with_plugins_and_settings` are the plugin-aware forms; the old functions delegate with `LoadSettings::default()`. (e) The template schema is pinned in a test by its FNV-1a 64 hash at `m4-done`. (f) `Scenario` and `ValidationReport` are not `#[non_exhaustive]`, so their new fields would break an outside struct literal or exhaustive pattern; no code does that (in-repo checked; M4 added `Scenario` fields the same way), so the change counts as additive. `Scenario`'s `PartialEq` now also compares `tick_rate_source`. Marking them `#[non_exhaustive]` would itself break M2-frozen API and is left to a deliberate later change. | The reader signatures are frozen; validate has no `Scenario` to inspect; the CLI needs the plugin-aware forms. | WI-3 (config file feeds `LoadSettings`) |
| ASM-169 | (M5 WI-3.) Config reader details. (a) The schema file lives with the other file schemas in `crates/umbra-templates/schemas/config.v1.schema.json` (the plan and ADR 0029 say `schemas/config.v1.schema.json`; the repository has no top-level `schemas/`), exported as `umbra_templates::CONFIG_FILE_SCHEMA` and printed by `umbra schema config`. (b) `schema_version` is optional; when present it is checked by a config-local copy of the template check (same codes and messages) against `umbra_templates::config::CONFIG_SCHEMA_VERSION = 1`, independent of the template/scenario `SCHEMA_VERSION` (`< 1` is `invalid_value`, a string is `wrong_type`, newer is `unsupported_schema_version` and nothing else is read). (c) `default_rate_hz <= max_rate_hz` is checked on the effective values, so `max_rate_hz = 20` alone fails against the default of 30; the error points at the key the file sets (the default key if both are set). (d) `allowed_origins` entries are `scheme://host[:port]`: lower-case scheme, non-empty host (a bracketed IPv6 literal is allowed), optional numeric port up to 65535, no path, query, fragment or user info; the host is lower case (upper case is `invalid_value`); the port is ASCII digits only; text in brackets must parse as an IPv6 address. `allowed_hosts` entries are only checked to be non-empty with no whitespace or `/` (ADR 0029 requires no more). (e) `[plugins] paths` entries must be non-empty. Counts and sizes are positive `i64` integers; seconds and rates accept integers or floats; `send_timeout_s` and `shutdown_grace_s` must also fit a `Duration`. (f) Relative `[plugins] paths` and `[server] scenario_root` join the directory of the file as given, so `./umbra.toml` yields `./plugins`. (g) `--config` is a global flag (accepted before or after the command); `schema` uses no setting but still fails (exit 1) on a missing or invalid named file. `--log-level` of `run` loses its clap default so the file can supply it (flag > file > `warn`). `[log] level` applies to `run` only, the one command with logging. The `info: using configuration FILE` line is written by `run` at `--log-level info` or more verbose, and only for a file named with `--config` (an implicit file gets the `note:` only); `validate` and `list-plugins` have no logging and write only the implicit-file `note:`. (h) The reader returns `Config` (`#[non_exhaustive]`, plain values: `Option` for keys without a built-in value, concrete defaults for `[server]`); `umbra-engine` re-exports `Config`, `ConfigError`, `LogLevel`, `ServerConfig`, `StreamConfig`, `load_config`. | Keeps `umbra-templates` free of server types and keeps the reader in the one located pipeline; the smallest rules consistent with ADR 0029. | WI-17 (serve consumes `ServerConfig`; `max_connections` and `allowed_hosts` semantics) |
| ASM-170 | (M5 WI-4.) Canonical events and `Kernel::remove` details. (a) `SimEvent::kind_name` returns `entity_created`, `entity_removed`, `fire`, `custom`, `simulation_control`: snake case of the variant, one name per variant, independent of the payload (the plan and ADRs leave the spelling open; the stream filter and DTOs use these). (b) The Events system reads the intents the Behavior phase left in each entity (route expansion already applied) and never touches them; `Fire` and `Custom` from Owned entities only. `TickReport::events` is a fresh `Vec` per tick (empty vectors do not allocate). (c) `Kernel::remove` updates the id index, the behavior slot map and the sensor-owner count together, then despawns; `next_id` is untouched so ids are never reused. `remove` also scrubs the removed id from every entity's `Contacts` (`retain`, between ticks, deterministic), so a snapshot taken right after `remove` never lists it; the next tick recomputes every contact list anyway, so no tick result changes. (d) The batch group buffers are rebuilt from the live entities at the start of every Behavior phase, so `remove` needs no group bookkeeping beyond one thing: when the removed slot was batched it calls `BatchScratch::begin_tick`, so the kernel stops holding the group `Arc` (a plugin batch) until the next tick instead of releasing it only then; `remove_a_batched_entity_releases_the_batch_between_ticks` observes this with `Arc::strong_count` (the plugin fixture test does not, its release is observable only through the behavior's own last owner). (e) The plugin row of AT-1 lives in `umbra-engine/tests/plugin_remove.rs` (the kernel may not depend on `umbra-plugin-host`, ASM-005): it observes `destroy_instance` of the fixture's `lifecycle` behavior at the call to `remove`. (f) The rustdoc of `Intent::Fire`, `Spawn`, `Despawn` and `Custom` in `umbra-core/src/intent.rs` was updated to the ADR 0028 wording (doc comments only; the file has no inline test region and no API changes). | Smallest rules consistent with ADR 0028 and the frozen M0-M2 files. | WI-5 (session emits `EntityCreated`/`EntityRemoved`), WI-6 (DTO kind names) |
| ASM-171 | (M5 WI-5.) `Engine::pump`, `Session` and confinement details. (a) `pump` waits `min(deadline, now + max_wait)` through `Clock::wait_until`, so it never sleeps past the next tick's deadline; `Pumped::Aborted` is returned instead of `EngineError::PluginFault` for the tick that ran (`Err` only when no tick ran). (b) `LoadSettings` gains `extra_plugin_paths` (searched before the scenario's, never confined: the configuration file is trusted) and `confinement`; `load_scenario_with_settings` ignores both, `Session::load` uses them. (c) `Session::load` and `load_scenario_with_plugins_and_settings` share `plugins::load_with_host_options(base, path, paths, settings, HostOptions)` (the body moved out of the public function, which delegates with `HostOptions::default()`; no public signature changed; plugins.rs is M4 code, not M2-frozen). It takes the resolved plugin directory list instead of `extra`, so a confined `Session::load` can pass the list built from the inputs it checked. `SessionOptions::plugin_log` (an addition to the plan's field list) feeds `HostOptions::log`, so the drop-order test can observe plugin calls. With a confinement `Session::load` refuses a non-file path (`ConfineError::NotAFile`) and builds the plugin list only from `extra_plugin_paths` plus the `plugin_dirs` of the `ScenarioInputs` it just checked (deduplicated like `resolve_plugin_paths`), never from a second parse; without one it uses `resolve_plugin_paths`. The plugin-aware loaders (`*_with_plugins_and_settings`) search `settings.extra_plugin_paths` after `extra`; `confinement` applies only through `Session::load`, and `load_scenario_with_settings`/`validate_path_with_settings` load no plugins and ignore both fields. (d) The per-placement build and spawn of `instantiate_in` moved unchanged into `scenario::spawn_placement`, which `Session::spawn` also calls with a `Placement` made from the template (no route, no overrides; the `entity` index in build errors is the scenario's placement count plus a counter of API spawns, so it never repeats after removals; the scenario registry for spawns is built once in `load`). It runs against `scenario_registry(session registry, scenario)`, recomputed per spawn. (e) `validate_graph` leaves out the file graph whose `id` equals the document's, found with the new lenient `umbra_templates::graph_document_id(&SourceFile)` (the loader's own parser; a syntax error after the `id` does not hide it; no `id` means nothing is left out). Other graphs are re-read from `GraphDef::origin`; an unreadable file becomes an `io` diagnostic made by `umbra_templates::io_diagnostic` (now `pub`, additive), which keeps the absolute path in its message: WI-11 must rewrite or strip it before it reaches a response (AT-19 `no_response_contains_an_absolute_path_outside_the_root`). (f) `Confinement::new(root, plugin_roots)` canonicalises its directories (`io::Result`); a request is normalised lexically against the root first (outside gives `PathNotAllowed` with the relative request echoed, or a fixed text for an absolute one, without any disk access), then links are resolved component by component with missing parts kept, so a missing path below a link out is refused too and a dangling link is refused. A `..` after a missing part makes the path unresolvable (refused). A missing path inside the root resolves to where it would be, for the loader to report (422). `check_inputs` resolves the raw (not lexically normalised) input paths, because `link/..` differs on disk, and also checks the scenario file. Display form (root-relative, although ADR 0026 says "relative to the scenario file"; an absolute request through an alias of the root such as /tmp versus /private/tmp is refused, which is conservative; `normalise` drops a leading `..` of a relative input): root-relative, `.` for the root, `plugins[<i>]/<rel>` in a plugin root, `<outside the scenario root>/<file name>` otherwise. (g) `scenario_inputs` lists every `*.toml` below the template directories (`files`, links to files as links), lenient and empty for a file that is missing or not a scenario. (h) Drop order: the field order of `Session` is the plan's, but the observable order (destroy calls, then `shutdown`) is also guaranteed by the host's image reference counts, so reordering the fields is not detectable from outside; the drop-order test pins the observable order, per entity (each placement builds its own behavior). | Smallest rules consistent with the plan, ADR 0024 and ADR 0026 (D-b). | WI-8 (`EngineHandle` uses `Session`), WI-11 (server resolves requests with `resolve_request`) |
