# Assumptions: M1

Part of the assumptions log; the index and the rules are in `docs/assumptions.md`.

## M1 Walking skeleton (recorded 2026-10-17 by architect, plan `docs/plans/M1.md`)

| ID | Assumption | Reason | Revisit when |
|---|---|---|---|
| ASM-026 | `umbra-engine` and `umbra-cli` are created in M1, minimally. `umbra-engine` is a synchronous facade (`Engine`, `EngineConfig`, `run`/`step` with a per-tick callback); no `EngineHandle`, channels or observers (M5). It re-exports the core/kernel types `umbra-cli` needs, because the rule table lets `umbra-cli` depend only on `umbra-engine` (and later `umbra-server`). | Gate 4 lives in `umbra-engine` (`docs/build.md`), the waypoint test needs kernel and motion together (kernel may not even dev-depend on motion, ASM-005), and the CLI deliverable needs a facade. Keeps the gate command unchanged. | M5 (EngineHandle) |
| ASM-027 | M1's CLI command is `umbra demo` (flags `--ticks`, `--seed`, `--rate`, `--clock`, `--print-every`, `--json`, `--log-level`). It runs the hard-coded scenario, prints entity state lines and a final `state_hash=<hex>`. `--json` emits JSON Lines via `serde_json::json!` (no serde derives). Output format is unstable until M2. `run scenario.toml` (REQ-S-1) arrives in M2. | REQ-X-2 has no command for a built-in scenario; a separate name avoids giving `run` a scenario-less form that M2 would have to break. Resolved 2026-10-17 (human): `demo` is removed in M2 (plan `docs/plans/M2.md` WI-11); the demo becomes the example scenario run with `umbra run` |
| ASM-028 | The hard-coded scenario lives in `umbra_engine::demo`: 3 ground entities near 52°N 4°E on flat terrain at 0 m, square routes of four 500 m legs, arrival radius 5 m, ground params from the spec 7.1 example (18 m/s, 40 deg/s, 2.5 m/s²); cruise speed jittered per entity from the `SCENARIO` RNG stream. Entity 1 is "the hard-coded entity". | Shared by the determinism test, the waypoint test and the CLI (DRY). Three entities make ordering bugs visible. M2: replaced by `examples/scenarios/walking_skeleton/` (M2 WI-11, ASM-061) and `umbra_engine::demo` deleted |
| ASM-029 | Route following in M1 is a kernel-internal stand-in system in the Behavior phase (`Route` component; emits `SetSpeed` + `MoveTo` each tick, `Hold` after the last waypoint; advances when within the arrival radius horizontally). The kernel exposes no public `System` trait in M1. | M1 must follow waypoints without a behavior runtime (M3). A public system-registration seam is designed when its second user (the behavior runtime adapter) exists (KISS). Hold is non-latching: the stand-in re-evaluates every tick, so an entity that drifts out of the final arrival radius is steered back to the last waypoint. | M3: remove the stand-in; route following moves to the behavior runtime (`FollowRoute`/`move_to`) |
| ASM-030 | `Intent` in M1 has only `MoveTo { destination: Ecef }`, `SetSpeed(MetersPerSecond)` and `Hold`, and is `#[non_exhaustive]`. Intents are re-emitted every tick and cleared before the Behavior phase. Resolution in a motion model: `Hold` wins; otherwise the last `MoveTo` and last `SetSpeed` win; no intent means decelerate to a stop; unknown variants are ignored. | REQ-B-2's other variants have no consumer before M3. Stateless models are simpler and deterministic. | M3 (full intent set and versioning) |
| ASM-031 | `MotionModel` (in `umbra-core`): `fn id(&self) -> &MotionModelId; fn step(&self, &KinematicState, &[Intent], Seconds, &dyn TerrainProvider) -> KinematicState`, `Send + Sync`, infallible, no state across ticks. Parameters are bound when the instance is constructed; entities share an instance through `Arc<dyn MotionModel>`. LSP contract checks are plain functions in `umbra_core::motion::contract` returning `Result<(), ContractViolation>`. | REQ-M-1 signature; only built-in implementations exist, so a fallible signature would be speculative. | M7 (motion-model plugin kind may need errors and per-entity params) |
| ASM-032 | `TerrainProvider` in M1 has `height_at` and `surface_normal_at` only; `line_of_sight` is added with perception in M3. `FlatTerrain { height }` is a constant height above the WGS-84 ellipsoid, normal = local up. `ground.kinematic` sets pitch and roll to 0 (it does not tilt to the surface normal in M1). | Terrain following needs only height; LOS semantics (earth curvature) are best decided with its first consumer. | M3 (LOS), or when non-flat terrain arrives (normal alignment) |
| ASM-033 | Coordinate conventions: ECEF in meters (`f64`); geodetic latitude/longitude in radians plus height above the WGS-84 ellipsoid, longitude wrapped to (-π, π], latitude validated in [-π/2, π/2]; ENU and NED tangent at an origin; orientation is a unit quaternion (Hamilton, active) rotating body FRD axes to ECEF; Euler helper = heading/pitch/roll relative to local NED (ZYX), heading clockwise from true north. ECEF to geodetic is closed form (Heikkinen/Zhu 1994), no data-dependent iteration (one fixed correction step allowed), finite for all finite input (radicand clamped at 0 near the polar axis; spherical fallback beyond 1e12 m where the intermediates would overflow). | D-15, REQ-C-3; matches DIS's ECEF-based orientation needs in M6; no iteration count that could vary with input. | M6 (DIS orientation mapping) |
| ASM-034 | `umbra_core::math` wraps every non-exact `f64` function (trig, inverse trig, exp/log, `powi` as a fixed-order product, `powf`, `cbrt`, `hypot`) and `clippy.toml` bans those direct methods, the hyperbolic ones that have no wrapper yet (add one to `math` if needed), and `mul_add` workspace-wide, not just in simulation crates. `math.rs` carries the only `#![expect(clippy::disallowed_methods, reason = "ADR 0003 ...")]`. `sqrt`, `abs`, `floor`, `to_radians`/`to_degrees` and `+ - * /` stay allowed (IEEE-exact). | ADR 0003: one swap point for `libm`. Workspace-wide is simpler than per-crate config and costs nothing outside simulation code. | If cross-OS determinism is required (ADR 0003 option 2) |
| ASM-035 | Wall time is read only through the `WallClock` trait (`now`, `sleep_until`). `StdWallClock` in `umbra-kernel/src/clock/wall.rs` is the only implementation using `Instant`/`thread::sleep`, with one module-level `#![expect(clippy::disallowed_methods, reason = "REQ-K-4: ...")]` in a private `mod real` of that file (its constructor and trait impl both need `Instant`). `ManualWallClock` (public) serves tests and embedding. The `Clock` owns `SimTime` and pacing; systems never see wall time. Real-time/scaled deadlines are computed from integer tick differences since an anchor, re-anchored on resume and mode change; when behind, ticks run back to back (never skipped) and `Clock::behind()` reports the lag of the tick just run: the wall time past that tick's own deadline, when it exceeds one (scaled) period. `set_mode` to the current mode is a no-op; leaving Stepped drops pending steps. `advance` anchors the schedule if no poll did. `TimeScale` is limited to [1e-3, 1e6]. | D-5, REQ-K-3, REQ-K-4, REQ-K-8: a single, reviewable wall-clock site; tests stay fast and deterministic. | M5 (commands may need a blocking wait in Stepped/paused) |
| ASM-036 | Tick semantics: tick `k` runs the phases with `now = SimTime(k)` and `dt`; afterwards the clock is at `k + 1`, and snapshots/hashes are labelled with the post-tick time. In M1 entities are spawned only between ticks (no in-tick spawn or despawn). | Simplest unambiguous rule; spawn/despawn intents come in M3. | M3 |
| ASM-037 | ECS ordering rule: `hecs` handles never leave `umbra-kernel`; `EntityId` (from 1, never reused) maps through a `BTreeMap`. Systems either treat entities independently or iterate in `EntityId` order; hashes and snapshots always walk `EntityId` order. | REQ-K-4 without relying on ECS storage order (ADR 0005). | When a system with cross-entity effects appears (M3 events) |
| ASM-038 | `SimRng`, `RngStream` and the canonical `StateHasher` are pure types in `umbra-core`; the kernel owns the instance and the per-entity `EntityRng` component (created at spawn, keyed by `EntityId`, hashed). Scenario-level randomness uses the `SCENARIO` domain keyed by placement index. | Behavior and motion crates may depend only on core, yet must receive RNG streams; the algorithm is pure math (ADR 0006/0007). | M4 (host API exposure) |
| ASM-039 | M1 snapshots are synchronous (`Kernel::snapshot()`, entities sorted by id). The bounded, drop-on-slow observer buffer of REQ-K-6 arrives with `EngineHandle` in M5. | No observer exists before M5. | M5 |
| ASM-040 | M1 benchmarks: `criterion` in `umbra-kernel` only (`benches/tick.rs`, 1k and 10k entities, stub constant-velocity model, because the kernel may not dev-depend on `umbra-motion`). Gate 14 is compile-only; the 15% regression rule (NFR-1) needs a stored baseline and is not enforced without CI. | Gate 14 names `umbra-kernel`; A-1 says optimize only when profiling demands it. Per-phase timing is deferred: only whole ticks are measured, with a stub model. | M9 (NFR-1 target), or when a baseline store is agreed |
| ASM-041 | `Ownership::Remote { source: RemoteSource }`, where `RemoteSource` is an opaque string label in M1. | REQ-K-5 needs the variant now (motion filter test); its exact identity (adapter capability id, M6) is not designed yet. | M6 |
| ASM-042 | Extends ASM-013: `clippy.toml` also bans `rand::random`, `rand::thread_rng`, `rand::rng`, `rand::rngs::OsRng`, `getrandom::getrandom`, `getrandom::fill` and `fastrand` entry points, and the types `hashbrown::HashMap`/`HashSet`, using `allow-invalid = true` where a path does not resolve in a crate. `rand` is not a dependency (ADR 0006); `proptest`'s use of it is test-only. | ASM-013 promised RNG bans in M1; `hecs` may bring `hashbrown` into the tree. | If clippy cannot express a ban (fall back to review) |
| ASM-043 | Logging: `umbra-kernel` uses `tracing` (`default-features = false`, `std`), with trace-level spans per phase and a `warn!` on overrun; `umbra-cli` installs `tracing-subscriber` `fmt` with a `--log-level` flag (no `env-filter`). | REQ-X-3 and REQ-K-8 at minimal dependency cost. | M5 (server logging), or when users ask for per-module filters |
| ASM-044 | Positions are stored only in ECEF (D-15); geodetic is derived on demand for terrain queries and display. At the user-facing edge (`umbra-engine` `SpawnSpec`/`RouteSpec`, later templates/scenarios in M2 and the API in M5) a position may be given as ECEF or WGS-84 lat/lon/alt via `umbra_core::coords::Position`, and is converted to ECEF exactly once at spawn. "Alt" is height above the WGS-84 ellipsoid (HAE); there is no geoid/MSL model in v1. Heading for geodetic placement is clockwise from true north in the local ENU frame. Output for display (CLI) converts back with `EntitySnapshot::geodetic`. | Human requirement 2026-10-17; keeps the simulation in one canonical frame while letting users work in lat/lon. | If MSL altitude is needed (geoid model) or another datum is required |
| ASM-045 | `contract::check_motion_model` treats an entity as stationary when its input velocity is exactly zero and its intents are empty or only `Hold`; it may then move by at most 1 mm. Determinism is compared bit for bit on two calls; the orientation norm must be within 1e-9 of 1. Case authors place stationary entities on the terrain, since a model may snap to it. | The plan lists the four violations but not the thresholds; these are the simplest values consistent with ground-model terrain following. | M8 (air/sea models) if their stationary behavior differs |
| ASM-046 | `Euler::to_quaternion` / `Euler::from_quaternion` live in `geo` (body FRD to NED, ZYX); `LocalFrame` composes them with the NED to ECEF rotation. At pitch +-90 degrees heading and roll are not separately recoverable (gimbal lock); the pitch argument of `asin` is clamped. | `LocalFrame` needs them and the plan puts "Euler helpers" in `geo`. | If a model needs full-attitude flight (air models) |
| ASM-047 | Demo layout (WI-13): entity `i` (0-based) starts at the corner `52.0 + 0.02 * i` N, `4.0` E, height 0 and follows four waypoints of a 500 m square, the last being its start corner. Entity 1 goes east first (clockwise), entity 2 north first (counter-clockwise), entity 3 east first (counter-clockwise). Initial speed 0, heading toward the first leg. `Engine::step` in a non-stepped mode runs until the tick count has grown by `n`; `Engine::rng()` exposes the master `SimRng` for scenario randomness. `RunSummary` has the field `ticks_run`. | The plan fixes the route shape but not the placement; corners 2.2 km apart keep routes disjoint. | M2 (scenario files) |
| ASM-048 | Ground model intent hardening (WI-8 review): a non-finite `SetSpeed` is treated as `SetSpeed(0)`; a `MoveTo` with a non-finite destination is ignored. A non-finite or non-positive `dt` returns the state unchanged (`MotionModel::step` precondition, documented in `umbra-core`). | Garbage must neither become full speed nor panic (`f64::clamp` panics on NaN bounds). | M3 (intent validation at the behavior boundary) |
| ASM-049 | `builtin.ground.kinematic` semantics: heading is a constant bearing in the local frame at the entity (rhumb-line-like; no great-circle steering), and poles are excluded for ground vehicles (observed trap: near 89.9995 N the local frame turns fast under the entity). Vehicles cannot pivot: the heading changes only while the new speed is positive, while a stopped vehicle with a destination behind it still accelerates (slowly, limited by the turning-circle term) and turns. Closes plan open question 4 (reverse and pivot turns) for M1. | KISS; keeps the model stateless and deterministic. | Air/sea models (M8) or a scenario that needs reversing or pivoting |
| ASM-051 | `Kernel::spawn` validates inputs once, in `world.rs`: the initial `KinematicState` must be finite (`KernelError::InvalidState`) and route waypoints finite (`InvalidRoute(RouteParam::Waypoints)`), next to the existing arrival radius and cruise speed checks (`RouteParam`). | Non-finite input must not reach the simulation (CLAUDE.md rule 6); the kernel is the last common entry for engine, tests and later network input. | M2 (templates validate earlier, with better messages) |
| ASM-050 | `TickReport.overrun` is the tick's own wall duration (end minus start, read through the clock's `WallClock`) minus its budget `Clock::wall_period()` (tick period divided by the time scale), set only when positive and only in RealTime and Scaled; each such tick logs one `tracing::warn!` with its per-phase timings and the budget. Schedule lag from `Clock::behind()` is reported separately as `TickReport.lag` and does not warn, so a single 500 ms stall gives one warning, not one per catch-up tick. | REQ-K-8 says a tick that exceeds its time budget produces a warning; measuring against the schedule would warn on every catch-up tick. Coordinator decision, 2026-10-17. | M5 (metrics may want both numbers) |
| ASM-052 | Engine edge validation: `Engine::new`/`with_wall_clock` return `Result` and reject a non-finite terrain height; `Engine::spawn` rejects non-finite heading or ECEF position and non-finite or negative speed (`SpawnParam`), leaving state and route finiteness to the kernel (ASM-051). | CLAUDE.md rule 6: no unchecked external numbers; the engine is the user-facing edge in M1. | M2 (templates validate earlier) |
