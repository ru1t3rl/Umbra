# Assumptions: M2

Part of the assumptions log; the index and the rules are in `docs/assumptions.md`.

## M2 Templates and scenarios (recorded 2026-10-17 by architect, plan `docs/plans/M2.md`; ADR 0008-0010 Proposed)

| ID | Assumption | Reason | Revisit when |
|---|---|---|---|
| ASM-053 | File discovery: a search path or `validate` directory is walked recursively; every regular file ending in `.toml` counts, in sorted path order; directory symlinks are not followed, symlinks to regular `.toml` files are, the extension match is case-sensitive (`.toml` only), and nesting deeper than 64 directories is an `io` diagnostic. One template per file; the file name need not match the `id`. A document with a top-level `scenario` table is a scenario, any other document is a template; scenario files found under `template_paths` are skipped there. `template_paths` are relative to the scenario file. | Simplest unambiguous rule; sorting makes loading independent of `read_dir` order (REQ-K-4); not following symlinks avoids loops. | If users need multiple templates per file or include/exclude patterns |
| ASM-054 | TOML is read with `toml` 1.1.8 `toml::de::DeTable::parse_recoverable(&str) -> (Spanned<DeTable>, Vec<toml::de::Error>)`: spans on every key and value, and every `Error` has `message()` and a byte-range `span()`. Confirmed in the WI-1 spike (scratch program parsing two independent bad lines reported both); it needs only the `parse` and `std` features, no extra flag; no `toml_edit` fallback needed. Syntax-error reporting (revised 2026-10-17 after the WI-1 review): (1) every parser error is reported, sorted by span; nothing is removed (several real errors on one line, e.g. two bad values in one inline table, are all kept). (2) Cascade rule: with `toml` 1.1.8 an unclosed array or inline table always runs to the end of the file, so the parser reports it last, at end of file, after a cascade of follow-on errors that start right after the opening bracket; no independent error can follow it. It is therefore reported once, at its opening bracket, and every other error between the bracket and the end of file is suppressed; independent errors before the bracket are kept and sorted before it (the parser lists the unclosed error first among them). Nested unclosed containers (an array inside an unclosed inline table, or the reverse) give two "unclosed" errors at one offset: each is reported at its own opening bracket, outermost first; an "unclosed" error is never suppressed by another's cascade rule, and a file with any parser error always yields at least one `syntax` diagnostic. The opening bracket is found in the partial tree as the outermost not-yet-used container of the right kind that starts with the bracket, does not end with its own closing bracket, and ends at the error offset (when the parser ended the partial container earlier, as for an inline table followed by more lines, the outermost unterminated container of that kind; the first cascade error is on the line after it, so "the first error's line" would be wrong); if none is found the error stays at its own (end of file) position and nothing is suppressed. A parser error without a span has no location and a note "position not reported by the parser". This depends on `toml`'s message text, so WI-4/WI-5 fixtures pin each case (two bad values in one inline table, two bad array elements, duplicate key plus a bad value, unclosed array followed by tables) and fail loudly on a `toml` upgrade. Values after an error may be placeholders (span `0..0`). (3) A file with syntax errors is not checked semantically, but its top-level `id` is recovered from the partial tree when its span is real, and that template is marked broken, so dependents in other files are not reported as `unknown_template` (ASM-056 no-cascade rule); if the `id` cannot be recovered, `unknown_template` errors in other files get a note "may be defined in <file>, which has syntax errors". Fixture: a broken file plus a valid child in another file that extends a template defined in it. No serde derives anywhere: readers walk the spanned tree by hand so every semantic error is collected (serde stops at the first). | REQ-T-2 "all errors"; a broken syntax tree gives unreliable follow-up errors. | If `toml` changes its spanned API |
| ASM-055 | `ComponentKind` has `MotionModel`, `Terrain`, `Behavior`, `Sensor`. M2 registers only `builtin.ground.kinematic` and `builtin.terrain.flat`; the behavior and sensor maps are empty until M3 adds their product traits. `[behavior]` and `[[sensors]]` sections are therefore read and checked structurally, and their IDs are `unknown_id` errors with the note that none are registered in this build (the spec 7.1 example does not validate in M2). `Terrain` is an engine registry kind, not an ABI capability kind (REQ-P-4 unchanged). | REQ-T-1: no special-casing of "not yet implemented" IDs; honest errors; OCP for M3. | M3 (behaviors, sensors), when a terrain plugin is designed |
| ASM-056 | Diagnostics: `path:line:column: error[code]: message` plus `note:` lines; line and column 1-based, column counted in Unicode scalar values, CRLF treated as one line break; codes are stable snake_case strings (`DiagnosticCode::as_str`); sorted by (path, byte offset, code, message) and deduplicated on (code, location, message). Only errors exist in M2 (no warnings). Dependents of a template with a set-level error (unknown parent, cycle, duplicate, error in its own file) are not resolved from the broken ancestor and produce no cascade diagnostics about it; they are still checked for what they state themselves: their own component IDs, their own `[[sensors]]` list, and their own parameters: in full (schema and trial build) when they name a different model than their nearest readable ancestor, otherwise key by key against the schema of the model they or that ancestor name, without `missing_param` (it depends on the merge) and without a trial build. An unknown `extends` is reported on every definition of a duplicated ID. Duplicate IDs are found across clean files and files with errors (the later definition in path order is the duplicate). | REQ-T-2; stable, reproducible output for scripts and tests. | If editors need byte or UTF-16 columns (LSP), or warnings are needed |
| ASM-057 | `schema_version` is a required integer in templates and scenarios, one shared `SCHEMA_VERSION = 1`. Newer is rejected and the file is not checked further; below 1 is invalid. "SHOULD migrate older" has nothing to migrate in v1: a future v2 adds a migration step over the v1 tree before semantic checks. Adding optional keys does not bump the version; removing, renaming or changing a key does (ADR 0010). | REQ-T-5 with KISS; one pipeline, one version. | First breaking format change |
| ASM-058 | Strictness: every template found in a scenario's `template_paths` is validated, not only the referenced ones, and any error fails the scenario. Every resolved template must name a motion model (no abstract templates). Unknown keys are errors everywhere. Component parameters are validated against the schema and then dry-run through `Factory::build`, so `validate` catches what spawning would. | One validation pipeline for `validate` and `run`; typos never pass silently. | If large shared template libraries make this too strict (add per-scenario template lists) |
| ASM-059 | Placements are always `Owned` (no ownership key in v1). `name` and `group` are optional strings; duplicate non-empty names are errors. They are engine-level metadata (`EntityInfo`), not ECS components, and not in the state hash (ADR 0007 unchanged). Entities spawn in file order, so ids follow file order. | REQ-K-5 (remote entities come from the network in M6); no consumer of names inside the simulation yet. | M3 (groups in behaviors), M5 (API by name) |
| ASM-060 | Scenario values: `seed` is a non-negative TOML integer (so at most `i64::MAX`); `tick_rate_hz` a positive integer (ASM-016); `duration_s` finite and > 0, run length `ceil(duration_s * hz)` ticks (at least 1, checked against `u64`); `clock` is `afap`, `realtime`, `stepped` or `scaled` with `time_scale` in [1e-3, 1e6] (mirrors `umbra_kernel::TimeScale`, which `umbra-templates` may not depend on; a `umbra-engine` test asserts the bounds agree). `[terrain]` defaults to `builtin.terrain.flat` with `height_m = 0`. Positions: `{ lat_deg, lon_deg, alt_m }` (alt above the WGS-84 ellipsoid, optional, default 0) or `{ ecef_m = [x, y, z] }`, exactly one form. TOML datetimes and `nan`/`inf` are rejected everywhere (parameters and network sections cross as JSON, REQ-P-6). TOML integers satisfy JSON Schema `number`. Units are given by key suffix (`_m`, `_s`, `_deg`, `_dps`, `_mps`, `_mps2`, `_hz`). | REQ-C-4 (units at the edge), ASM-044, ASM-016; KISS. | Fractional rates (human said no), seeds above `i64::MAX`, MSL altitude |
| ASM-061 | The example scenario `examples/scenarios/walking_skeleton/` reproduces the M1 demo layout (corners 52.00/52.02/52.04 N 4 E, 500 m squares, same leg directions, arrival radius 5 m, flat terrain at 0 m, 30 Hz) with three templates and fixed cruise speeds (15, 14.5, 17 m/s) instead of the demo's RNG jitter. So the seed no longer changes motion in this scenario; the different-seed determinism test asserts different hashes through the hashed entity RNG state only. `umbra_engine::demo` and `umbra demo` are removed (human, 2026-10-17). | Scenario files have no randomness feature in v1 (KISS); the human asked to reproduce the demo where practical. | M3 (behaviors that draw from `SimRng` make the seed matter again) |
| ASM-062 | `Engine` API changes in M2: `EngineConfig` loses `terrain_height`; constructors take an `Arc<dyn TerrainProvider>` (built by the registry; `TerrainProvider` is implemented for `Arc<T>`); `run`/`step` callbacks return `ControlFlow<()>` so `umbra run` stops on an output write error (M1 carried item); `RunSummary.stopped_early`. CLI exit codes: 0 ok, 1 invalid input or runtime error, 2 usage. | Terrain is chosen by ID now (REQ-C-6, REQ-T-1); closes the M1 write-error item. | M5 (`EngineHandle`) |
| ASM-063 | Component IDs are globally unique across kinds (one namespace, ADR 0002): `Registry` keeps a `BTreeMap<ComponentId, ComponentKind>` index and a registration whose ID is held by any kind is `RegistryError::Duplicate` naming the existing kind. `BuildError.param` is an RFC 6901 JSON pointer relative to the params root (`/max_speed_mps`); `Duplicate.kind` is `ComponentKind` (plan said `&'static str`). | A template names a component by ID alone (REQ-T-1, D-8); a shared ID across kinds would make diagnostics and the GUI ambiguous. KISS. | If a plugin legitimately offers a model and a sensor under one ID (M3/M4) |
| ASM-064 | A `BuildError.param` JSON pointer resolves to the span of its deepest existing ancestor in the located TOML tree, so a missing key (`/max_accel_mps2`) points at the params table. `umbra-templates` (WI-7) implements the mapping. | Absent keys have no span; the nearest enclosing value is the most precise honest location (REQ-T-2). | If editors want insertion-point locations |
| ASM-065 | `builtin.ground.kinematic` schema bounds: `max_speed_mps` <= 1000, `max_turn_rate_dps` <= 3600, `max_accel_mps2` <= 1000 (all > 0). Enforced by the schema only; `build` checks positivity (via `GroundKinematic::new`) but not the upper bounds. The M1 and example values (5-22 m/s, 30-40 deg/s, 1.5-2.5 m/s2) are well inside. | Rejects absurd values (and 1e308 overflow in the integrator) at load time with a located error; KISS. | If a vehicle class exceeds them (aircraft models in a later milestone have their own factory) |
| ASM-066 | Scenario file details the plan left open. `[scenario]` requires `name`, `seed`, `tick_rate_hz`, `duration_s`; `clock` defaults to `afap`, `template_paths` to none, `[[entities]]` may be absent; an entity requires `template` and `position`, while `heading_deg` and `speed_mps` default to 0. `arrival_radius_m` and `cruise_speed_mps` must be > 0, `speed_mps` >= 0. `duration_ticks` is `ceil(duration_s * hz)` except that a product within two ULPs of a whole number of at least 1 is that number, so `0.1 s` at 30 Hz is 3 ticks, not 4 (the literal float product is 3.0000000000000004); a tiny positive duration is 1 tick; the result must fit `u64`. `[entities.overrides]` accepts only `motion` (`model`, `params`) in v1. An entity without overrides reuses its template's checked motion (no second trial build). When template paths could not be read (missing directory, non-UTF-8 file) the `io` diagnostic is reported and unknown entity template names are still reported, with the note "may be defined under <path>, which could not be read" (like ASM-054 rule 3). The duration guard is two ULPs of the product around a whole number of at least 1; a tiny positive duration is 1 tick, never 0; a product at or above 2^64 does not fit. An override that switches the model is located in the scenario. | KISS; a float artefact must not add a tick to a user's whole-tick duration; one trial build per template keeps `validate` and `run` identical. | If users want fractional-tick durations to round up strictly, or more override targets (behavior, sensors in M3) |
| ASM-067 | `umbra-templates` entry points: `Loader::load_scenario(path)` reads `template_paths` (relative to the scenario file, recursively, scenario files skipped); a file without a top-level `scenario` table and without syntax errors is `not_a_scenario`. `validate_path` on a directory checks all `.toml` files as one template set and each scenario file through the same pipeline as `load_scenario`; `files_checked` is the sorted union of every file read. A directory's own template files are validated as one set; each scenario in it is resolved against exactly the templates `load_scenario` would build for it (its own `template_paths`, relative to the scenario file), so `validate` and `run` agree. Files are read once and each distinct template set is loaded, and its components built, once. A single template file is checked in the context of its own directory, direct siblings only, not subdirectories (so a sibling parent resolves and an unrelated same-id template deeper in the tree is not a false duplicate) and only diagnostics located in it, or with a note pointing into it, are reported. Unreadable paths are `io` diagnostics: unlocated for the path itself, located at the `template_paths` entry for a missing template directory. | One pipeline for `validate` and `run` (ASM-058); deterministic order (ASM-053). | If `validate` needs per-scenario reports |
| ASM-068 | Schema subset strictness beyond ADR 0009, for M4 plugin authors: (a) any cycle in the compiled schema graph is rejected, including one through `properties` or `items` (recursive tree schemas are not supported), not only a pure `$ref` loop; (b) a schema whose `$ref` expansion (nodes visited by one validation, shared definitions counted per use) exceeds 10 000, or that has more than 10 000 subschemas, is rejected at compile time; (c) `$ref` names are JSON-pointer decoded (`~1`, `~0`); (d) integers are compared exactly against whole-number bounds, other comparisons use `f64`. Values that `parse` already reported as `unsupported_value` (datetime, non-finite float, integer outside 64 bits) are skipped silently by readers and schemas so they cause no follow-on errors. Opaque `network` tables still reject those values (ASM-060). | Fail-closed, deterministic and bounded validation cost for untrusted plugin schemas (NFR-2). | If M4 plugin authors need recursive schemas (raise limits or add depth-bounded recursion) |
| ASM-069 | `builtin.terrain.flat` schema bounds: `height_m` in [-1000, 10000] m above the ellipsoid, enforced by the schema only; `build` checks presence and numeric type (JSON numbers are always finite). Terrain supplied by an embedder through `Engine::new` is not validated; the ground model keeps the moved height if a provider returns a non-finite height (engine test `non_finite_terrain_heights_keep_the_state_finite_and_the_run_deterministic`). | Same approach as ASM-065; rejects absurd values at load time with a located error; KISS. | If terrain below -1000 m or above 10 km is needed (e.g. other bodies) |
